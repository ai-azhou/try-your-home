# 4 工具连接：改改你的家和 Agent 怎么配合

**什么时候读**：用户在改改你的家（本 app）里点了「交给 Agent」，把一段文字粘给你时；用户在「待核对」里答了问题、把答复交回来时（4.6）；用户用服务模式打开了方案、让你改文件时。

从 Skill v1.1 起这篇随 Skill 交付，工具仓库里也有同一份。工具本身另外下载：https://github.com/ai-azhou/try-your-home （Gitee 镜像 https://gitee.com/gevoll/try-your-home ），用户怎么拿到、怎么打开、什么时候开服务模式见 [交付.md](交付.md) 6.7。事实来自 `src/core/handoff.ts`（交接文字）、`src/core/questions.ts`（问题卡状态）、`scripts/serve.mjs`（服务模式）、`src/ui/actions.ts`（轮询和保存）、`src/ui/model.ts`（各模式下显示的是哪份方案）。

## 4.1 「交给 Agent」那段文字

用户在工具里选中构件、写一句话，复制出来的文字长这样。下面是 core 的 `agentHandoff` 对格式篇 1.8 的样例方案（另加了一条待确认改造 `ch-1`）在「改造」模式下实际生成的（直接打开文件、不是服务模式，所以方案文件那一行不是完整路径；选中了承重不明的隔墙 `w-mid` 和房间 `r-study`）：

```text
改之前先读 Agent 手册「格式」；涉及拆改再读「改造」3.2–3.6。Skill 内在 references/，工具内在 docs/agent手册/；工具连接 4.3 说明改文件的规矩。
```

逐段是什么：

| 段 | 内容 | 怎么用 |
| --- | --- | --- |
| `方案文件` | 只有服务模式下是方案的**绝对路径**。浏览器里直接打开文件（包括 4.2 说的连接文件）时，这里是文件名（如 `方案.json`）或方案里存的旧相对路径；演示方案、新建方案写「未指定」 | 绝对路径就改这个文件。不是绝对路径时，请用户告诉你文件的完整位置，不要猜，也不要在当前目录里找到同名文件就改 |
| `当前模式` | 原始 / 改造 / 对比 / 装修 | 决定改哪里，见 4.4 |
| `单位` | 固定一行 | 和 [格式.md](格式.md) 一致 |
| `## 选中构件` | 每个构件前一行楼层，再一行描述。墙：类型、名称、长厚高、端点、矢高、两侧房间（按法向分）、墙上洞口；洞口：宿主、offset、宽高、端点、两侧房间；梁：端点、宽、梁底；房间：层高、地面抬高、面积、顶点；柱、管井、楼梯、挑空：整个对象的 JSON | 用 id 在文件里定位。描述里的数字是**当前模式下看到的**：改造、对比、装修模式显示的是重放全部改造记录之后的结构（pending 也重放；缺 confirm 的受保护改动被跳过，看不到），和文件里原始数组的值可能不同，不要把它们抄回原始数组 |
| `## 用户原话` | 用户写的那句话；没写是「（没写）」 | 这是用户意图的唯一来源 |
| 最后一行 | 结构模式是「按 Skill 的改造说明追加 changes，承重先问」；装修模式是「装修写入 decor……不写入 changes」 | 见 4.4，原始模式下按用户意图判断，不一定追加 changes |

装修模式下，后面还会接一段 `## 装修构件（ref）`，见工具仓库里的装修篇（目前是占位，不随 Skill 交付）。

用户在「待核对」里答过问题、交接时附上了答复（工具里点「把答复交给 Agent」，或在「交给 Agent」里勾着「附上待核对答复」），`## 选中构件` 前面会多一节（没选构件时，选中构件一节只有一行「（没选构件）」）：

```text
## 待核对答复（2 条，等你处理）
方案文件里还没有这些答复：先按下面原文写进对应问题卡的 answer、answeredBy、answeredAt，status 写 answered，再处理。处理方法见读图 2.8「答复之后」、工具连接 4.6。
- q-kitchen（原始信息）
  问：厨房朝餐厅、朝客厅这两面，图上只画了细双线，没有画门……
  问的是：w-kit-e、w-kit-s、o-kit-slide
  答：开放式，没有门（业主 · 2026-10-30）
- q-heights（原始信息）
  问：层高、窗台高、门高图上都没有……
  答：就按这些（业主 · 2026-10-30）
```

- 服务模式、连接文件时工具会先把答复存回方案文件，第二行换成「这些答复已经存进方案文件（status 是 answered）……」，你直接处理文件里的就行。
- 工具里除了答复还有别的改动没导出时，多一行「工具里还有答复以外的改动没导出……」：要一起处理就请用户先导出方案文件（[交付.md](交付.md) 6.7「我改好了」）。
- 用户对你上一轮的处理有异议、又答了一次的卡，「答：」后面多一行「上一轮：答「…」，你回复「…」。这次是用户有异议。」
- 怎么处理见 4.6。

## 4.2 服务模式

```sh
node scripts/serve.mjs <方案所在目录> [端口]     # 在工具仓库（try-your-home）目录运行，端口缺省 5180；先 npm ci、npm run build
```

- 怎么帮用户开起来、怎么结束（只结束你自己启动的那个 PID）见 [交付.md](交付.md) 6.7。
- 只监听 `127.0.0.1`。终端打印 `打开：http://127.0.0.1:5180/?plan=方案.json`，目录里每个 .json 一行。
- 页面只能读这个目录里的文件（跳出目录、符号链接指出去一律 403）。响应头 `X-Plan-Root` 给出目录绝对路径，页面据此在交接文字里写方案的绝对路径。
- **轮询**：页面每 2 秒带 ETag（文件大小 + 修改时间）问一次方案文件。文件变了：
  - 页面上**没有未保存的改动** → 自动重新载入，提示「Agent 已更新」，视角保持不变；
  - **有未保存的改动** → 不覆盖，弹出提示，用户自己选「载入」或「稍后」。选「稍后」后，同一个版本不再提示。
- **保存**：用户按 ⌘S，页面 `POST /save?plan=<文件>`。服务只允许写目录里**已经存在**的 .json，先写同目录临时文件、fsync、再改名（原子替换）。写回的是 v3 规范格式（键排序、2 空格缩进），`meta.planFile` 存相对路径、`meta.updatedAt` 存日期。页面记得自己刚保存的版本，不会把它当成 Agent 的更新。

### 连接文件（不用开服务）

用户在 Chrome 或 Edge 里双击打开工具，再打开或拖入方案文件，工具会记住这个文件（记的是浏览器发的文件句柄，工具并不知道完整路径）。效果和服务模式基本一样：

- 每 2 秒比一次文件的修改时间和大小。文件变了，页面没有未保存改动就自动载入，有就先问「载入」或「稍后」。
- 用户按 ⌘S 或点「保存」写回原文件，第一次浏览器会问写入权限。写之前核对文件有没有被改过，被改过就不写，提示他选择载入还是先导出。
- 刷新页面读文件的最新内容；有没写回的改动时恢复改动，不被文件盖掉。关掉浏览器再打开，要点一下「重新连接」。
- 你照 4.3 用「写临时文件再改名」的方式改文件，工具能读到。

怎么判断：工具顶栏文件名旁边写着「Agent 改完会自动刷新」就是连着的（服务模式或连接文件）；写「已自动保存」就没连着。Safari、Firefox 没有这个接口，打开文件只读一次，Agent 改完要重新打开。

## 4.3 Agent 改文件的规矩

1. **改之前重新读文件**。用户可能刚在工具里保存过，不要用你记忆里的旧版本覆盖。
2. **只改要改的地方**：读出整个 JSON，改目标字段，其余原样写回——包括你不认识的字段、`meta`、`legacy`、`decor`、`underlay.src` 里很长的 data URL。不要从头重建方案。
3. **原子写**：写同目录临时文件，再改名覆盖，页面轮询不会读到半个文件。例（以格式 1.8 的样例为例；目标 id 先在文件里确认存在、没被前面的改造删掉）：

   ```sh
   python3 - "$WORK/交付/方案.json" <<'PY'
   import json, os, sys, tempfile
   path = sys.argv[1]
   plan = json.load(open(path, encoding='utf-8'))
   plan['changes'].append({"id": "ch-7", "op": "remove", "type": "wall", "target": "w-glass",
                           "by": "agent", "status": "pending", "note": "拆掉客厅和书房之间的玻璃隔断"})
   fd, tmp = tempfile.mkstemp(dir=os.path.dirname(path), suffix='.tmp')
   with os.fdopen(fd, 'w', encoding='utf-8') as f:
       json.dump(plan, f, ensure_ascii=False, indent=2)
   os.replace(tmp, path)
   PY
   ```

4. **写完立刻校验**：`validate`；动了 changes 再 `apply`（[改造.md](改造.md) 3.6）。失败就修好再停手，不要把坏文件留给页面载入。工具有三层保护：页面读到有错误的文件时不替换当前方案，只提示一次；载入失败以后保存和导出都被拦下；本地服务写回前会再校验一次，有错误、或者要用空方案覆盖有内容的文件都会拒绝。但这些只防止数据被清空，用户在页面上会看到「没有载入」的提示，体验很差——所以 validate 不通过的文件仍然一秒都不要留在服务目录里。
5. **告诉用户看哪里**：改了哪些 id、在哪个房间、该切到哪个模式看（原始 / 改造 / 对比），有没有 pending 等他在工具里点「我确认」。提醒：页面没有未保存改动会自动刷新；有的话要点「载入」，而载入会丢掉他没保存的改动——先保存或先让你停手。
6. 用户在工具里正在改、还没保存时，不要写文件；先请他保存。

## 4.4 按模式决定改哪里

| 当前模式 | 用户说的是 | 怎么改 |
| --- | --- | --- |
| 原始 | 读错了、答复问题（「这面是承重墙」「梁底 2.6 米」） | 纠错：直接改原始数组，写 `evidence.confirmed`（[读图.md](读图.md) 2.8）；答的是问题卡的，处理完在卡上写回复（4.6） |
| 原始 | 想拆、想改 | 改造：追加 changes，并提醒用户切到「改造」模式看 |
| 改造 | 想拆、想改、想加 | 追加 changes；受保护改动先问（[改造.md](改造.md) 3.4），记录写 `by:"agent"`，用户没明确同意的写 `pending` |
| 对比 | 一般是问问题 | 只读；要改就按上面两行判断 |
| 装修 | 装修相关 | 装修篇还是占位、不随 Skill 交付：告诉用户结构以外的装修数据现在不由你写，`decor` 原样保留，不写 changes |

目标 id 以文件为准。改造模式下选中的可能是改造产生的构件（如局部拆墙后的 `w-a~ch-3`、改造新增的墙），它们不在原始数组里，只能用 changes 去改。

## 4.5 用户贴来给网页 Chat 用的两段内容

工具里还有两个按钮是给网页 Chat 用的，用户也可能把它们的内容贴给你：

- **「复制问题给 Chat」**：校验出来的问题清单（错误码、说明、构件 id）、各房间面积、还没答的问题卡（含追问），以及「已答、等你处理的问题卡」（问题原文和答复）。按 [命令.md](命令.md) 5.4 的错误码去改 `$WORK` 里的方案；已答的那几条按 4.6 处理（文件里还没有答复就先用 `plan-cli answer` 记进去）；改完照常校验、重出、交付。
- **「复制方案给 Chat」**：一份完整方案，但不带底图编码（`underlay.src` 不是 data URL）。它可能比你手上的新：用户在工具里改过。不要直接覆盖 `$WORK` 里嵌了底图的方案：先问清它是不是最新版；是的话备份旧文件，把它存成新的 `方案.json`，`validate` 通过后用 `embed_underlay.py` 重新嵌入原图，再按 [交付.md](交付.md) 6.7「我改好了」那几步往下走。

工具还能认出网页 Chat 输出的「简版」方案：只按房间自动生成墙和门洞（没有窗户），界面上标明「简版」。Chat 输出的格式根本不对时，「复制问题给 Chat」给 Chat 的是简版模板，不是问题清单；用户把这段贴给你时不要照着写。用户拿简版生成的方案来找你，墙、门洞、窗都要对着户型图重新读，别当成读过图的结果。Agent 一律输出完整 v3，不要输出简版。

## 4.6 「待核对」的答复：处理完写回复、改状态

问题卡有状态（[格式.md](格式.md) 问题一节）：`open` 待回答、`answered` 已答等你处理、`resolved` 已处理。用户在工具的「待核对」里能看到每张卡的状态、你的回复和你改到的构件，所以**每条答复处理完都要在卡上写回复**，不能只在对话里说。

答复从这几处来：

- 交接文字里的「## 待核对答复」（4.1）。
- 用户说「我在工具里答了」「答完了」：请他在工具里点「把答复交给 Agent」把文字发来。服务模式、连接文件时点这一下会先把答复存回文件；没连着的，文字里有答复原文，或者导出方案文件按 [交付.md](交付.md) 6.7「我改好了」那几步换进来。
- 用户在对话里直接回答了问题卡。

步骤：

1. **改前重读文件**（4.3 第 1 条）。用户在工具里还有没保存的改动时先请他保存（服务模式 ⌘S）。
2. `node "$SKILL/scripts/plan-cli.mjs" questions "$WORK/交付/方案.json" --status answered` 列出要处理的卡（精简 JSON，不带底图，不用把整个文件读进上下文）。
3. 文件里还没有的答复（直接打开文件时交来的文字、对话里答的）：用 `plan-cli answer <方案> <问题id> --text "<用户原话>"` 记进去，`--by` 缺省「业主」，`--at` 用交接文字里的日期。问题 id 在文件里找不到，先问用户，不要猜是哪一张。
4. 逐条按 [读图.md](读图.md) 2.8「答复之后」选 outcome 处理；要改结构的改原始结构、写 `evidence.confirmed`。
5. 每条用 `plan-cli resolve <方案> <问题id> --outcome <…> --reply "<一句白话>" [--changed id,id]` 写回复。它只改那一张卡、原子写回、写完自校验，status 会按 outcome 改好（`ask` 回到 open，其余 resolved）。
6. `validate`；有 `changed` 的回到 SKILL 第 4 步，按原始结构改了处理（两组模型和图都重出）；只写了回复、没动几何的只重出叠图（[交付.md](交付.md) 6.1 第 4 条）。
7. 在对话里逐条回复用户：每条一句，和 `reply.text` 一样；说清改了哪些 id、哪条还在等他（追问的、没答的）。告诉他在工具里哪里看：顶栏写着「Agent 改完会自动刷新」的，页面自己会更新，提示「Agent 处理了 n 条答复」；没连着的，请他重新打开 `交付/方案.json`。

不要：

- 改用户的 `answer`、`answeredBy`、`answeredAt`，或替用户写答复；
- 把没答的卡写成已处理（撤回要有理由，写在 `reply.text` 里，用 `withdrawn`）；
- 写了 `resolved` 却没有 `reply`，或者手改 status 不写回复；
- 一张卡没处理完就去改下一张的结构——一条一条来，每条写完回复再下一条，中途出错也知道停在哪。

例（用户答了两条：厨房「开放式，没有门」、层高「就按这些」）：

```sh
P="$WORK/交付/方案.json"
node "$SKILL/scripts/plan-cli.mjs" questions "$P" --status answered
# 改结构：厨房朝餐厅的推拉门改成门洞（按 4.3 改原始数组、写 evidence.confirmed），validate 通过后：
node "$SKILL/scripts/plan-cli.mjs" resolve "$P" q-kitchen --outcome changed --changed o-kit-slide \
  --reply "朝餐厅那面的推拉门改成门洞，不装门；朝客厅那面还是墙。"
node "$SKILL/scripts/plan-cli.mjs" resolve "$P" q-heights --outcome confirmed \
  --reply "层高 2800、窗台 900、飘窗台 450、门高 2100 都按这个，模型不用改。"
```
