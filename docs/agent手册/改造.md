# 3 改造：拆、改、加怎么记

**什么时候读**：用户说要拆墙、开洞、挪门、改房间，或者交接文字的模式是「改造」时；`apply` 或 `--state renovated` 报错时。

规则来自 `src/core/changes.ts`（`applyChanges`、`validateReplay`）和 `src/core/mesh.ts`（`modelPlan`）。

## 3.1 先分清：纠错还是改造

| | 纠错 | 改造 |
| --- | --- | --- |
| 什么情况 | 读图读错了；用户答了问题卡（「这面是承重墙」「梁底 2.6 米」） | 用户想改变现状：拆、挪、加、改类型 |
| 改哪里 | 直接改原始数组（walls、openings、rooms……），在构件 `evidence.confirmed` 记下确认 | **原始结构不动**，往 `changes` 末尾追加记录 |
| 出图 | 原始模型和图都要重出 | 用 `--state renovated` 出改造后的模型和图；原始的不用重出 |

只有修改原始结构（纠正读图）才让原始那组模型和图过期；只追加或修改 changes，只影响改造后那组。问题答复、证据文字或内嵌底图没有改变结构时，不让白模过期；叠图在问题卡变化后要更新。

拿不准用户是在纠错还是在提改造，就问一句。

## 3.2 改造记录长什么样

`changes[]` 按数组顺序重放。每条：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | 是 | 全方案唯一，如 `ch-1` |
| `op` | 是 | `add` 新增 / `remove` 拆除 / `update` 修改 |
| `type` | 是 | `wall` `opening` `beam` `room` `column` `shaft` `stair` `void` |
| `target` | remove、update 必填 | 目标构件 id（可以是前面改造产生的 id，如局部拆墙的 `w-a~ch-3`） |
| `data` | add、update 必填 | add 写**完整构件**（含新 id，长度 mm）；update 只写要改的字段，不能改 id |
| `range` | 否 | 只对 remove wall：`[起,止]`，沿墙中心线从 a 端量 mm，只拆这一段 |
| `note` | 否 | 一句白话：想做什么、哪里是近似 |
| `group` | 否 | 同一次操作的多条记录共用一个 group（拆墙同时封门） |
| `by` | 是 | 谁写的记录：Agent 写的填 `agent`；`user` 是用户在工具里自己做的 |
| `status` | 是 | `pending` / `confirmed`，见 3.3 |
| `confirm` | 受保护改动必填 | `{"by":"业主","at":"2026-10-29"}`，见 3.4 |
| `at` | 否 | 时间字符串 |

例子：在 [格式.md](格式.md) 1.8 的最小样例上追加这些记录（都用 mm）。`apply` 结果是 ch-1 到 ch-5 成功，ch-6 返回 needsConfirm（外墙上的窗加宽，还在等用户确认，属于预期）；`export --state renovated` 只重放前五条，成功。

```json
[
 {"id":"ch-1","op":"remove","type":"wall","target":"w-glass","by":"agent","status":"confirmed","group":"g-open","note":"拆掉客厅和书房之间的玻璃隔断"},
 {"id":"ch-2","op":"update","type":"room","target":"r-living","data":{"name":"客厅书房","poly":[[120,120],[2940,120],[2940,2000],[3060,2000],[3060,120],[5880,120],[5880,3880],[120,3880]]},"by":"agent","status":"confirmed","group":"g-open","note":"两间打通，房间合并"},
 {"id":"ch-3","op":"remove","type":"room","target":"r-study","by":"agent","status":"confirmed","group":"g-open"},
 {"id":"ch-4","op":"remove","type":"wall","target":"w-mid","range":[0,500],"by":"agent","status":"confirmed","note":"隔墙北端拆掉 500 做通道"},
 {"id":"ch-5","op":"add","type":"opening","data":{"id":"o-east","wall":"w-e","offset":1000,"width":900,"kind":"window","sill":900,"head":2400},"by":"agent","status":"confirmed","confirm":{"by":"业主","at":"2026-10-29"},"note":"东外墙新开一扇窗，用户已二次确认"},
 {"id":"ch-6","op":"update","type":"opening","target":"o-win","data":{"width":2000},"by":"agent","status":"pending","note":"建议书房窗加宽到 2000（外墙，待确认）"}
]
```

各类型能做什么：

- **add**：八类都行。data 是完整构件，id 不能和已有 id 重复；洞口必须有有效的宿主墙且不和同墙洞口重叠；楼梯的起止楼层必须存在且向上；挑空必须写有效楼层。
- **update**：八类都行。合并后的构件要满足 [格式.md](格式.md) 的约束；改墙不能让墙上的洞口越界或高度失效。改弧墙 `bulge` 时，越界的洞口会被夹回墙内（单个洞口比新墙长还宽会缩宽并给 warning；几个洞口总宽放不下则整条拒绝）。
- **remove**：墙、洞口、梁、房间、柱、楼梯、挑空可以删；**管道井、烟道一律不能删**（见 3.5）。只有墙支持 `range` 局部拆除，其他类型都是整件删。
- 拆墙后，**房间不会自动合并**：两间打通要另写 update room（改 poly）或 remove room，否则两个房间多边形仍各自存在。
- 局部拆墙：拆掉中间一段，剩下两段，第一段沿用原 id，第二段 id 是 `墙id~改造id`；落在拆除段内或跨过拆除边界的洞口随之删除，其余洞口挂到剩余段并换算 offset。拆掉墙头或墙尾只剩一段时，沿用原 id。

**拆半面墙，range 怎么定**：先从用户的话里找两端（如「从洞口边到外墙」），投影到宿主墙中心线，按 a 端起算；不能把「打通」擅自解释成整墙或某个整数长度。墙上有洞口时，必须明确问「洞口跟着剩下的墙保留，还是这次一起拆掉？」。例如墙长 5000 mm，a 端在北外墙，洞口 offset=2000、width=900：用户确认「拆北外墙到洞口北边，洞口保留」，range=[0,2000]；剩余墙沿用 id，洞口保留并换算 offset=0。若确认连洞口段一起拆，range=[0,2900]，洞口随之删除。`apply` 的 affected 表示保留但受影响（例如重挂、换算 offset），removed 才是删除；再核对重放结果和新图。

**T 形相接、支墙端点正对洞口**：端点仍放在主墙中心线上，不要用停在墙面的方法掩盖冲突。先核对图，再调整洞口 offset 避开支墙占据的相接区；涉及猜测就进问题卡，不能为了校验通过悄悄挪洞。对于垂直相接的直墙，洞口边至少离交点一个支墙半厚（例如支墙厚 200 mm，交点沿主墙 s=2400，则洞口应止于 2300 或起于 2500 之外）；这是几何上避免相撞的距离，不是施工净距。**当前代码没有 T 接点到洞口的固定最小间距校验**，不能宣称有额外 50 / 100 mm 的校验规则。现有 validate 只要求 offset≥0、offset+width≤墙长（容差 0.00001 mm），同墙洞口不得重叠（同容差）。端点斜接的 1 mm 容差也不是洞口净距。斜交、弧墙按实际占地核对并看叠图、白模。

## 3.3 pending 和 confirmed

| | pending（待确认） | confirmed（已确认） |
| --- | --- | --- |
| 含义 | Agent 的提议，用户还没点头 | 用户明确要做这个改动（看过提议后同意，或本来就是用户提出的） |
| `apply` | 检查 | 检查 |
| `export / render / cameras --state renovated` | **不重放**，不出现在改造后的模型和图里 | 重放 |
| 工具里 | 显示成淡紫色提议，带「我确认 / 撤销这条」 | 正常显示 |

- 用户在对话里明确要求、范围也说清了（「把次卧和客厅之间这面墙拆掉」）→ `confirmed`。
- 你自己的建议，或者用户的话有不止一种理解（「这边开敞一点」）→ `pending`，问清后改成 `confirmed`。
- `status:"confirmed"` **不能代替** `confirm`：受保护改动两样都要。

## 3.4 哪些改动要用户二次确认

下列改动没有 `confirm`（或 `confirm.by` 为空）时，重放返回 `needsConfirm:true` 并跳过这一条，不执行：

**承重墙、外墙，以及承重情况不确定的墙**（原始结构里 `evidence.certainty` 是 `unknown`，即使 kind 暂记为 partition；或 kind 原始是 `bearing` / `exterior`、重放途中曾经是）：

- 整面或局部拆除；
- 挪动端点 `a` / `b`、换楼层 `level`、改弧形 `bulge`；
- 减薄 `thickness`、降低有效墙高（比较这条墙记录前后的有效高度）、降低 `lowHeight`；
  - 注意：改房间 `ceiling` 也会间接让旁边的墙变矮，接口不会为此要求确认，但它同样在动结构，照样先问用户；
- 改类型 `kind`（任何改动，包括改成 partition、half、glass）；
- 在墙上新增洞口；把洞口挪到这面墙上；在这面墙上挪动洞口（offset 变化）、加宽、降低洞底、抬高洞顶。

**承重柱**（`columns[].kind` 原始是 `bearing`，或重放途中曾经是）：删除、挪动中心、任一边尺寸变小、改类型或形状、旋转、换楼层。

保护身份**跟着构件走**：先带 confirm 把承重墙改成隔墙，之后再挪动或拆它，仍然要再确认一次；原始 certainty 为 unknown 的墙也不能靠改证据绕过确认；局部拆除剩下的分段也继承保护。

**不需要**二次确认的：改名、加厚、加高、加大尺寸、缩窄或删除受保护墙上已有的洞口（封洞）、改证据说明；certainty 为 `inferred` 或 `seen` 的普通隔墙拆改（不因推断而要求二次确认），以及其他非承重构件的改动。这些改动仍要通过几何校验。

**怎么问**（原话示例，按情况改）：

> 这面是外墙（按图读出来的，不一定准）。在外墙上开窗会动到结构，能不能做要现场和专业人员判断。你确定要我在方案里试这个改动吗？这只是看效果，不代表可以施工。

用户回答「确定」后，记录写 `"status":"confirmed","confirm":{"by":"业主","at":"2026-10-29"}`（by 写确认人；工具里固定写「业主」，用户自称别的就照写，不写 agent）。用户没回答，就保持 `pending`、不写 confirm，交付时说明这条在等确认、不在改造后的图里。

## 3.5 管道井、烟道

- `remove` 一律报错「管道井 / 烟道不能拆」，带 confirm 也不放行。
- add、update（挪位置、改轮廓、改类型）接口允许，但这只是数据能力，不代表工程上可以挪。
- 用户要拆管井：告诉他方案里不能记这条改造，原因是管井通常连着上下楼层的公共管线，要不要动以物业和专业人员意见为准；可以写一张 `category:"renovation"` 的问题卡记下他的意图。

## 3.6 改完一定要重新校验、重新出图

**受影响的那组模型和图必须重出，不能交付与对应结构不一致的旧图。** 每次改了 `changes`（或改了原始结构）：

1. `node "$SKILL/scripts/plan-cli.mjs" validate "$WORK/交付/方案.json"`：字段和原始几何。
2. `node "$SKILL/scripts/plan-cli.mjs" apply "$WORK/交付/方案.json"`：逐条重放**全部**记录（含 pending）。看输出：
   - `results[]`：每条 `ok`；`ok:false` 时看 `needsConfirm`（缺二次确认）和 `error`；`affected` / `removed` 是受影响的构件 id；`warnings` 是夹回洞口之类的提示。
   - `issues[]`：重放后的最终方案的几何问题，每条带 `changeIds` 指出是哪条改造引入的。
   - 退出码 1 时：如果唯一的问题是**你知道正在等用户确认的 pending 受保护改动**返回 needsConfirm，可以继续；其他任何 `ok:false` 或 `issues` 里的 error 都要先修。
3. `node "$SKILL/scripts/plan-cli.mjs" export "$WORK/交付/方案.json" "$WORK/交付/改造后/白模.glb" --state renovated`：这一步只重放 confirmed，并对最终结构做完整校验，有 error 直接拒绝（exit 1，不写文件）。它通过了，改造后的结构才算有效。
4. 重出改造后的图：`render ... --state renovated`，至少一张斜视，加上用户关心的房间平视。改造后的输出放单独的文件夹（如 `交付/改造后/`）。
5. 打开新图看一眼：拆掉的墙确实不见了、新开的洞在对的位置。
6. 如果改的是原始结构（纠错），原始的 GLB、斜视、俯视、平视、叠图全部重出；有改造时也重出改造后那组。只改 changes 时，保留原始那组。

交付前按 [交付.md](交付.md) 6.1 只检查受影响的那组，不用整个 JSON 的修改时间判定原始图过期。

## 3.7 常见报错

| 输出里的 error | 原因 | 怎么修 |
| --- | --- | --- |
| `削减、移动、改类型、拆除或开洞承重墙、外墙、承重情况不确定的墙需要用户二次确认`（needsConfirm） | 受保护墙改动缺 confirm | 按 3.4 问用户；确认后补 confirm，未确认保持 pending |
| `削减、移动或拆除承重柱需要用户二次确认` | 同上，承重柱 | 同上 |
| `管道井 / 烟道不能拆` | remove shaft | 删掉这条记录，见 3.5 |
| `目标 xxx 不存在` | target 拼错，或目标已被前面的记录删掉 | 查 id；注意局部拆墙后的新 id |
| `id xxx 已存在` / `分段 id ... 已存在` | add 的 id 重复 | 换一个唯一 id |
| `更新不能修改构件 id` | update 的 data 里改了 id | 去掉 data.id，或写成 remove + add |
| `缺少 data 参数` | add / update 没写 data | 补 data |
| `宿主墙 xxx 不存在` | 新洞口挂在不存在（或已拆）的墙上 | 换宿主墙 |
| `洞口尺寸缺失或超出墙长` / `同墙洞口重叠` / `洞底、洞顶与墙高不相容` | 新洞口几何不对 | 改 offset、width、sill、head |
| `拆除区间必须在墙长范围内，且起点小于终点` | range 越界 | range 用 0 到墙长之间的值 |
| `新墙长不足以容纳所有洞口，未修改墙和洞口` | 改 bulge 让墙变短 | 先删或缩窄洞口 |
| `墙更新导致洞口 xxx 无效：...` | 改墙让洞口越界或高过墙 | 一起改洞口，或换个改法 |
| `改造最终校验失败：room-self-intersection ...（改造 ch-x）` | 改造后的最终结构有几何错误 | 按 changeIds 找到那条记录修正，错误码含义见 [命令.md](命令.md) 5.4 |
