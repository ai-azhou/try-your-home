# 2 读图：从户型图到方案

**什么时候读**：拿到户型图、开始定比例和读结构之前；遇到看不懂的线型、色块、文字时；面积对不上时；决定要不要问用户时。

本篇只讲读图的一般规律。图形惯例只是候选判据，**不能据此认定真实承重或施工条件**；判断写进 evidence，会改结构又读不出来的进问题卡。

## 2.1 先给图分类

| 看什么 | 为什么 |
| --- | --- |
| 你是否真的看到了图像 | 看不到就直说，不凭文件名猜 |
| 电子示意图 / 开发商或平台户型图 / 手机翻拍 / 手绘 | 翻拍要先查透视（2.2），手绘尺寸只能当参考 |
| 现状图还是改造意图图 | 改造图上的虚线、彩色墙段可能表示拆除或新建，要分开问 |
| 有没有图例、尺寸链、房间面积、指北针、楼层标注 | 决定比例来源和问题清单 |
| 一张图里有几层 | 并排画几层就每层一份 `levelUnderlays` |

## 2.2 定比例

**有比例依据时，至少两个独立来源**，例如横、竖两条尺寸链，或一条尺寸链加房间标注面积。同一尺寸换种写法不算独立。门宽 800–900、墙厚 240/120 只是常见范围，不能当实测。

**图上完全没有比例依据**（没有尺寸链、面积或比例尺）：允许先按常见构件尺寸假设比例，例如把图上一扇 90 px 宽的门洞假设为约 900 mm，得到约 10 mm/px；这不是实测，也不能把按该比例算出的外轮廓当成第二个独立来源。必须进问题卡，`underlay.calibrations` 的 `note` 明写「假设：门宽约 900 mm，非实测」，相关尺寸保持推断。用户答「不确定，按最可能理解」也不升级 certainty。交付说明**第一句**写「尺寸是按常见门宽估的」，再说用了什么假设及其影响。

给用户的原话示例：

> 这张图没有尺寸、面积或比例尺。我先把门洞宽按常见的约 900 mm 估，做一版看结构；所有长度和面积都会受这个假设影响。你有任意一面墙的实测长度或一间房的面积吗？没有也可以先看，我会把这项保留为推断。

交付开头示例：

> 尺寸是按常见门宽估的：图上没有比例依据，我暂把门洞按约 900 mm 换算，长度和面积都待实测核对。

**找尺寸链的刻度端点**：尺寸链是一条细线，每段两端有刻度，常见三种画法：45° 斜短线、垂直短线、实心点或箭头。端点取**刻度与尺寸线的交点**，不是斜线的端头。做法：

1. 把尺寸链所在区域裁出来放大看（用 Pillow 裁切、放大 4–8 倍，保存成新图再看，原图不动）；
2. 尺寸线是水平的就沿它所在的像素行找深色像素，斜刻度会在这一行留下一两个像素宽的深色点，取它的中心列；
3. 每个刻度记一个像素坐标，段长 p = 相邻刻度像素差。

例：上方尺寸链刻度在 x = 60.5、510.5、735.5、1110.5 px，标注 3600、1800、3000 mm，三段 p = 450、225、375，都是 8.0 mm/px。

**多段拟合**：各段像素长 p、毫米长 L，s = Σ(p·L) / Σ(p²)，横竖分别得 sx、sy。同时核对总链与分段和、对边、单段残差。只用清楚、独立的读数。

**偏差**：|s1 − s2| / min(s1, s2) × 100%。**任意两个独立来源差 3% 以上就进问题卡**，不要平均掉冲突，也不要输出假精确的尺寸。sx 与 sy 明显不同先查图片是否被拉伸；确实不同就分别写 `mmPerPx` 和 `mmPerPxY`。

**翻拍**：先查透视——同一长度在图的不同位置量出不同比例，就要先校正图片或请用户给正拍图；横竖两个比例不能当作透视已消除。不足两个可信来源，停在问题卡。

**记录**：每个来源在 `underlay.calibrations` 记一条（原图两点、长度 mm、note 写来源和口径；无比例依据时明确写假设长度而非实测）。比例改了，已有墙和房间不会自动缩放，要重算几何和问题框后重新叠图。图片缩放或裁切过，像素框、原点、比例要一起更新。

## 2.3 像素换算成 mm

X = (x − ox) × sx，Y = (y − oy) × sy；反过来 x = X / sx + ox。

- **原点**：先判断尺寸链量的是轴线（墙中心线）还是墙外皮——刻度落在墙带中间是轴线，落在墙带边缘是外皮。国内户型图的尺寸链多数是轴线。是轴线时，取横竖两条链的第一个刻度作原点，读出来的就是墙中心线坐标。
- **墙中心线**：墙带两条边线的中点。**墙厚** = 墙带像素宽 × s，取整到常见值前先看相邻墙是否一致；读不准的厚度写 inferred。
- **洞口 offset**：从宿主墙 a 端沿中心线量到洞口近端的门框。先确定墙的 a、b 是哪一端，再量。
- **墙与墙相接**：L 形、十字形转角，两面墙的端点写成同一个坐标（相差不超过 1 mm 才算同一接点，工具会自动斜接）；T 形相接，支墙的端点放在主墙的中心线上。端点没对齐会在模型里留缝或出现突出的墙头。一面长墙被门窗打断时不用拆成几段，写成一面墙、洞口挂在上面。
- 坐标取整到 10 mm 左右即可；比图的精度更细的小数没有意义。
- **有门窗线、没有墙带**（例如厨房一侧只画了推拉门线，两边没有墙）：门窗必须挂在墙上，补一面宿主墙，`kind` 写 `partition`、厚度用缺省 120，`certainty` 写 `inferred`，basis 写「图上只有门窗线，没有墙带，补的宿主墙」，不写 pixelBox；进问题卡问「这里是一道墙带门，还是只有门、两边是开敞的？」。

**墙的 certainty 说的是「这面墙是什么类型」的把握**，不是「看没看见这面墙」。它决定拆改要不要二次确认（[改造.md](改造.md) 3.4）：

| 情况 | certainty | 例 |
| --- | --- | --- |
| 图上标了承重、外墙，或画法明确（图例写明、在外轮廓上） | `seen` | 图例「黑色 = 承重墙」；外轮廓上的墙 |
| 按画法推断是隔墙 | `inferred` | 空心双线墙带、带细线分格的灰带，图例没说明 |
| 看得见墙，但看不出承不承重 | `unknown` | 内部黑色实心粗墙带，没有图例、没有标注 |

`unknown` 的墙即使 kind 暂记 `partition`，拆、挪、削、开洞都要先问用户。墙的**位置**读不准（端点、厚度），不靠 certainty 表达：写进 basis（「墙厚估读」），会改结构的进问题卡。

## 2.4 图例与画法

先看图例和标注，再看线型组合和相邻构件，最后才按惯例猜。

| 图上看到 | 候选解释 | 怎么核、怎么写 |
| --- | --- | --- |
| 粗实心连续墙带（黑） | 结构墙，或统一填黑的墙 | 对照图例、墙厚、连续性。**不能单凭实心判承重**。没有承重信息时内墙写 `partition`、certainty `unknown`，basis 写「图上无承重信息」，所有这类墙合并成一问 |
| 空心双线墙带 | 常表示非承重隔墙，也可能只是不填充的画法 | 核对厚度和连接。不要把空心墙当玻璃 |
| **灰色墙带**（比黑墙浅的实心或填灰带） | 非承重隔墙（很多图例用填灰表示）、矮墙或栏板、半墙玻璃、玻璃隔断 | 灰度本身不定类型，同一张图里可能有几种灰。看：图例；和黑墙比的厚度；位置（厨房台面边、阳台外沿多是矮墙或栏板，房间之间多是隔墙）；带内有没有细线分格（有分格多是玻璃）。读不准就写最可能的 kind，certainty `inferred`，`lowHeight` 用缺省 1000，同类灰带合并成一问：「这些浅灰构件是矮墙、栏板还是玻璃？多高？」 |
| 单线 | 构件边界、尺寸引线、隔断、家具轮廓 | 查端点和标注，不自动补墙 |
| 墙洞内三四条平行细线 | 窗（窗框） | 墙外的多线可能是尺寸链或家具，先确认位置 |
| **洞口内两条平行细线，没有门扇也没有开启弧线** | 门洞 / 垭口 `doorway` | certainty 写 `inferred`；有推拉轨道或多条门扇线时按推拉门 `sliding` 处理，拿不准进问题卡，不直接当窗 |
| 墙洞内两条错开的细线 | 推拉门或推拉窗 | 结合洞口在哪面墙（外墙上落地的多是阳台推拉门） |
| 门洞旁弧线加一条直线 | 平开门 | 开向和铰链侧见 2.5；弧线被遮住时不自行猜开向 |
| 门洞两侧只有墙端、无门扇无弧线 | 门洞 `doorway` | |
| 窗外侧另有一圈细线框、或标「飘窗」「凸窗」 | 飘窗 `bay-window` | 外框说明窗向外凸出：按图把凸出部分的三面墙画出来，窗挂在凸出的墙上 |
| **只有文字「飘窗台」「飘窗」、没有窗台轮廓** | 室内有窗台，深度和是否外凸未知 | 窗写 `bay-window`（sill 用缺省 450，inferred）。不要编窗台轮廓；问「窗台多深、多高、是否凸出外墙」。用户给了深度，再按 [格式.md](格式.md) 的飘窗台写法加一个 `floorOffset:450`、`counted:false` 的房间，并把主房间 poly 让出这块。单间面积偏大可能和它有关，见 2.7 |
| 外墙外侧一圈细线或栏杆符号，没有窗扇 | 未封阳台 `open-balcony`，或空调平台 | 平台写成 `counted:false` 的房间 |
| **穿过房间的虚线**（两端搭在墙上或悬空） | 梁的投影、吊顶或天花分界、上层构件投影、挑空边、地面材质或功能分区；改造图里还可能是拆除线 | 有标注（「梁」字、梁底或梁高数值）就照标注画梁，`seen`。没有标注：判断依据是两端是否搭在墙或柱上、是否和上层墙对齐、线型是否与图例一致。读不准是什么，**默认不画**，进问题卡（框住这条虚线），问「这条虚线是梁、吊顶分界还是别的？如果是梁，梁底离地多高？」。用户想先看大致效果时，可以画成梁、certainty `unknown`、`bottom` 用 2500 并在 basis 写明是假设，但问题卡照问、交付说明照说 |
| 墙角或房间中的实心小方块、小圆，比墙厚略大 | 柱或墙垛 | 是否和墙带连成一体、多层是否同位。写进 `columns`；kind 拿不准写 `bearing` 加 certainty `unknown` |
| 厨卫角落带斜线或交叉线的小方块 | 烟道、管道井、风道；也可能是设备或柜体 | 写进 `shafts`，kind 拿不准写 `other` |
| 一组等距平行短线加箭头或「上」「下」 | 楼梯，箭头多指上行 | 短线条数和转折决定 straight / L / U / spiral；复式里核对两层是否同位 |
| 房间内交叉线、虚线大框，或标「挑空」「上空」 | 挑空或楼板开洞；也可能是上方构件投影 | 上层写 `voids`，下层房间照常写；拿不准进问题卡 |
| 门口或分区处几条短平行线、标高差字样 | 台阶或地面高差 | 写房间 `floorOffset`；数值没有标注就问 |
| **房间没有写名字** | 按位置和设施推断用途 | 结合灶台、洗手池、马桶、床等，name 写推断名称、certainty 写 `inferred`、basis 写依据；设施也没有时可写「左上间（用途待核）」。用户提到的房间（如「厨房和客厅之间」）和推断对不上，先问清是哪两间、哪面墙，再动改造 |
| 填色块 | 功能区域、改造标记、家具示意 | 颜色本身不能确定用途或材质 |
| 浅灰小块、家具轮廓 | 家具、固定柜体、设备 | 结构阶段不写 |
| 弧线墙带 | 弧墙 | 见 2.6 |
| 不同颜色的墙段、红绿标记 | 改造图里的拆除或新建 | 现状和改造分开：现状写原始结构，改造写 changes 并先问意图 |

`extract_drawing.py` 的 `walls / thin / gray / color` 是按像素颜色分出的**候选**，不能直接当已确认的结构。它的 `walls` 只收近黑色（RGB 都小于 90）的粗块，`gray` 只收非常浅的灰（家具底色那种）；中灰的墙带两边都不收，最多在 `thin` 里留下碎线——灰色墙带要自己看图读。

## 2.5 门的开向和铰链侧

平开门在图上画成：一条门扇线（门开到约 90° 时的位置，一端在门框上）+ 一段四分之一圆弧（从门扇线的另一端画回对面门框）。

1. **铰链在哪个门框**：门扇线与墙相接的那个门框就是铰链所在，也是圆弧的圆心。
2. **hinge**：那个门框是洞口的近端（离宿主墙 a 端较近，位于 offset 处）写 `"start"`；是远端（offset + width 处）写 `"end"`。
3. **side**：门扇线和圆弧画在墙的哪一侧。取宿主墙 d = b − a，n = (−dy, dx)；在门扇线上取一点 P，墙中心线上取一点 Q，算 (P − Q)·n：为正写 `1`，为负写 `-1`。
4. 先确认门挂在哪面墙上：门框两端都落在同一面墙的洞口里才算；拐角处的门要看洞口在哪面墙的墙带里断开。

例：书房门挂在 `w-f`（a=[2400,4800] → b=[6000,4800]），offset 1100、宽 900，两个门框在 x=3500 和 x=4400。门扇线竖直画在 x=4400、向下（y 变大）伸进书房。x=4400 是 offset + width 处 → `hinge:"end"`。d=(3600,0)，n=(0,1) 指向下；门扇在下方，(P − Q)·n > 0 → `side:1`。

双开门（两段弧线）：模型在直墙上只会画成一整扇门，`panes` 对平开门不起作用；按整个洞口写一扇门，`name` 或 basis 写明「双开门」，并列进附录。推拉门、门洞不写 `swing`。弧线被家具或文字挡住、看不出开向时，写缺省 `{"hinge":"start","side":1}` 并把这扇门的 evidence 写 `inferred`，开向不影响结构的话不必进问题卡，列进附录。

## 2.6 弧墙

弧墙仍写成一面墙：a、b 是弧的两个端点（中心线），`bulge` 是**矢高**——弦中点到弧中心线的距离，单位 mm，正负看方向。

- 直接量：弦长 c = |b − a|，弦中点到弧中心线的像素距离 × s 就是矢高。
- 已知半径 R：矢高 = R − √(R² − (c/2)²)（劣弧）。
- 方向：d = b − a，n = (−dy, dx)。弧往 n 那侧鼓，`bulge` 取正；往反侧鼓，取负。交换 a、b 会让 n 反向，`bulge` 也要变号。

例：东侧弧墙从上往下画，a=[7200,1500]、b=[7200,5100]，d=(0,3600)，n=(−1,0) 指向左（西）；弧最东点在 x≈7650，往东鼓 450，和 n 相反 → `"bulge":-450`。

弧墙上的洞口 offset、width 按弧长量。弧墙旁的房间 poly 用几段折线逼近弧的内皮即可。

## 2.7 面积对照

叠图时把图上标注的房间面积传给 `overlay.py --labels "书房=9.8,客厅=24.5"`，它逐间打印方案面积、标注面积和有符号偏差，超过 5% 标【超过 5%】。

房间标注面积常见三种口径：墙内净面积、按墙中心线围成的面积、含墙面积。方案里的 poly 永远是**墙内净边界**，不为凑标注去挪墙或改边界。

- **整套都偏同一方向、偏差相近**：多半是口径不同，不是比例错。用墙内边界、中心线、墙外边界各算一遍，找到一致的口径写进附录；找不到写「口径不明」。
- **只有一间偏、其余都吻合（单间偏差）**：比例没问题，问题在这一间。按顺序查：
  1. 叠图上这间的 poly 是否压在墙的内皮上，有没有漏掉或多画一块；
  2. 这间有没有图上画了但不计面积的部分：飘窗台、凸窗、设备平台、管井、阳台。算一下候选部分的面积（例：1800 × 500 的窗台 = 0.90 m²），和偏差量比；
  3. 标注本身可能是另一种口径或印错。

  能解释就在附录写「书房方案 10.72 m²、标注 9.80 m²，差 0.92 m²，与飘窗台 1800×500 接近，推测标注不含窗台」；这个推测如果会改结构（窗台深度、是否外凸），进问题卡。解释不了就如实写偏差和已排除的原因。
- 总面积只能在口径一致时用来校验；套内、建筑、使用面积不能混用，总面积也定不出长宽。

## 2.8 问题卡

**问什么**：每个候选问题过两关——答案会不会改方案里的墙、洞口、梁、柱、楼层或高度？图上是不是确实读不出来？两关都过才问。能从图上读出的不问；只影响面积口径、不改几何的不问，写进附录。

- 同类合并成一问：「哪些墙是承重墙」「这些浅灰构件是什么、多高」「层高和窗台高」。用 `targets` 列出涉及的构件，不按构件逐个问。
- 第一轮 3–5 问、不超过 5 问，阻塞结构的排前面。8 问是全部轮次累计的上限，不是目标。
- 几处不相邻的同类构件（例如三条分散的虚线、几段浅灰带）合成一问，`targets` 列全，`bbox` 可以不写——一个框框不住分散的几处。
- 没进问题卡的推断照常写进构件的 evidence，并在附录列出。
- 层高、窗台高、门高图上都没有时合并成一问，写明你暂用的缺省值。
- 改造图另问拆墙意图、色块背后的用途；只问清楚，不替用户布置。

**怎么写**：字段见 [格式.md](格式.md)。

- `text` 问事实或意图，用用户听得懂的话，可以说明「图上看到了什么」；不用二选一逼用户确认，`options` 只是方便，用户可以自由回答。
- `bbox` = [左,上,右,下] 平面 mm，只框有歧义的那一个或几个相邻构件，四周留一个墙厚左右的边距。问整屋性质的问题（层高、承重、图和现场是否一致）不画框，只写 `targets`。
- 叠图发现框超过整层 1/4 面积，只画角标并在终端警告：缩框或去掉框。

**答复之后**：

答复可能从三处来：用户在「改改你的家」的「待核对」里答（交接文字里有一节「## 待核对答复」，服务模式下文件里已经是 `answered`）；用户在对话里直接答；用户导出方案文件说「我改好了」。不管从哪来，都按下面处理，再按 [工具连接.md](工具连接.md) 4.6 的步骤写回文件。要处理的是 `status` 为 `answered` 的卡（`plan-cli questions <方案> --status answered` 列出来；没有 status 的老文件，是有答复、没有 reply 的卡）。

- 用户在对话里答的，先用 `plan-cli answer` 把原话记进这张卡（`answeredBy` 写「业主」），再处理。这样工具里看到的记录和对话一致。
- 每条答复选一个 outcome（[格式.md](格式.md) 问题一节的表），照做：
  - `changed`：答复和读图不一致。按答复改**原始结构**（这是纠错，不是改造），改到的构件写 `evidence.confirmed = {"by":"业主","at":"日期","note":"答复要点"}`，certainty 改成符合实际的值；`reply.changed` 列这些 id。
  - `confirmed`：答复证实了现在的读法。几何不动，targets 里用户确认到的构件写 `evidence.confirmed`。
  - `inferred`：用户说「不确定，你按最可能的来」「不知道」。按推断保留，certainty 不升级，不写 confirmed。
  - `noted`：答复不涉及结构（偏好、以后的打算）。记下，不动结构。
  - `ask`：答复还不够（「我量一下告诉你」、有歧义）。不动结构，`reply.text` 写清你还要知道什么；卡回到待回答。
  - `withdrawn`：不用再问了（比如答别的问题时已经弄清楚、构件已经改掉）。`reply.text` 写为什么。
- 一个答复只覆盖用户实际确认的内容。用户没回复就保持待答，不把等待或默认选项当成答复，也不替用户写答复。
- 每处理一条就用 `plan-cli resolve` 写 `reply`（outcome、一句白话 text、changed），它会把 status 改对；不要改用户的 `answer*`。`reply.text` 就是你在对话里对这一条说的话，两边一致。
- 叠图保留所有问题：未答红框；已答等处理橙色虚线框；已处理灰色虚线框（大框仍用角标，无 bbox 的仍留图例）。outcome 是 `inferred` 的图例写「已处理，仍是推断」；没有 reply 的老文件，answer 里有「不确定」「不知道」「不清楚」「按最可能」「最可能的」「按图上最可能」「按图推断」「你看着办」时写「已答，仍是推断」。这是文字提示，不替代 evidence 的确定度判断，也不会自动改 certainty。
- 答完一轮再问下一轮，新问题 `status` 写 `open`。有 `changed` 的回到校验、叠图和出图（SKILL 第 4、6 步）；只写了 reply、没动几何的只重出叠图。

## 2.9 叠图核对看什么

`overlay.py` 把方案画回原图：墙按类型半透明上色，门窗是墙上的粗线段，房间是虚线轮廓，图内是编号小圆点，文字在右侧图例栏。逐项看：

1. 每面墙的色带压在原图墙带上，厚度一致；
2. 门窗线段落在原图洞口里，长度一致；
3. 房间虚线贴着墙内皮；
4. 柱、管井、楼梯、挑空的位置；
5. 终端打印的面积对照（2.7）和问题框警告。

对不上就改方案再叠，直到对上为止。**叠图前方案必须先通过 `validate`**：`overlay.py` 经 CLI 读方案，仅在确认方案校验失败时提示「先跑 validate」并显示原因。先读真实报错：缺依赖、Node、文件或字体问题按提示处理；不要把所有失败都当成方案错误。叠图打开看的是 PNG 本身——用你的看图能力实际看，不要只读终端输出。

方案统一写入 `$WORK/交付/方案.json`，原图留在 `$WORK/`；`underlay.src` 相对方案文件所在目录，例如 `../户型图.png`。交付前嵌入原图。
