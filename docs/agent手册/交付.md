# 6 交付：给用户的东西和说法

**什么时候读**：第 0 步给用户讲路线图时（6.6）；出完模型和图、准备交给用户之前；用户回来改了以后再次交付之前；每次交付末尾写「下一步你可以」时（6.7）。

## 6.1 交付前检查

按顺序跑完，全部通过再写说明：

1. `validate` 无 error。
2. 有改造记录：`apply` 只剩你知道的 pending 受保护改动返回 needsConfirm；`export --state renovated` 成功（见 [改造.md](改造.md) 3.6）。
3. 叠图是最后一版方案画的，打开看过。
4. **首次交付跳过过期图检查；只在改过方案以后检查。** 原始结构改了，原始和改造后两组都重出；只改 `changes`，只重出改造后那组。问题卡只有答复、回复或状态变了，只需重出叠图；按答复改了结构（有 `reply.changed`）就是原始结构改了，两组都重出；证据文字或嵌入底图不改变白模。按修改记录核对受影响的模型、图和相机文件是否已重出，旧文件移出交付目录。没有记录、不能确认是否对应当前结构时，重出对应那组；不要只凭整个 JSON 的修改时间判断。
5. `check-glb.mjs` 对每个 GLB 报 0 error。
6. 问题卡都写在方案 JSON 的 `questions` 里，和说明里的问题一一对应。
7. 交付前用 `embed_underlay.py` 把原图嵌进方案，以后用工具打开能直接显示底图；嵌入只改变底图存储，不需重出白模。

## 6.2 文件放哪

原图留在 `$WORK/户型图.png`，方案从开始就写在 `$WORK/交付/方案.json`。未嵌入时 `underlay.src` 相对方案文件目录写 `../户型图.png`；交付前嵌入原图。目录约定：

```
交付/
  交付说明.md        给用户看的一屏说明
  附录.md            比例、面积对照、推断清单、假设、没做的检查
  方案.json          结构方案（改的就是它）
  叠图.png
  白模.glb
  白模图/            iso-sw、iso-ne、top（各带 .camera.json）
  房间平视/          用户想看的房间
  改造后/            有改造时：白模.glb 和改造后的图
  生图素材/<房间>/   白模、深度、线稿、分割、提示词与打分记录
  效果示意/          用户要了效果示意图才有（生图.md）
```

过程文件（裁切的局部图、`extract_drawing.py` 的输出、你写的辅助脚本）放 `交付/` 外面，不混进交付物。

## 6.3 交付说明：一屏以内，讲三件事

白话，不堆术语，不贴 JSON。下面是要点和一个例子，不是固定措辞。

**1. 拿到了什么**：逐个列文件，每个一句话说用途。

- 方案 JSON：按图读出的结构底稿；以后要改就改它，再重新出模型和图。
- 叠图：读出的墙和门窗画回原图上，彩色压在原图的墙上说明读对了，对不上的请指出来。
- `.glb` 白模：可以旋转、缩放的三维模型。
- 白模图、房间平视：有改造时另附改造后的图，并说清哪些改动在图里、哪些还在等确认。
- 用户要了生图素材，再列素材文件夹；出了效果示意图，每张写明「效果示意，尺寸以平面和立面为准」（[生图.md](生图.md) 8.8）。

**2. 怎么打开**：只讲客观事实，不替用户挑软件。

- PNG 用任何看图软件打开。
- 方案 JSON 可以用配套的离线网页工具「改改你的家」（try-your-home.html）打开，叠底图、看 3D、自己拖墙试改造（6.7）。
- `.glb` 是 glTF 2.0 标准三维文件，支持 glTF 的查看器和建模软件都能打开（例如 Blender 自带 glTF 导入）。
- 网页上的在线查看器要把文件交给那个网站处理；户型属于隐私，用不用由用户决定。
- GLB 单位是米，Y 轴朝上；模型里有墙、门窗、玻璃、梁，没有家具和材质。

**3. 要你确认的几件事**：对应问题卡，一般 3–5 条，每条一句话，说清答案会改动哪里。再加：

- 比例来源和偏差；有对不上的面积在这里说一句。
- 用了缺省值的高度（层高、窗台、门高），列出来请用户核对。
- 模型和图上看不出来、容易误会的地方：例如「飘窗现在只是一扇窗，没有窗台」「那条虚线还没画进模型」。
- 还在等确认的改造（pending）：说明它不在改造后的图里。
- 结尾一句：这是按图读出的结构，不是施工图；承重和拆改的可行性要现场和专业人员确认。

问题可以在对话里直接答，也可以在「改改你的家」的「待核对」里答：答完在工具里点「把答复交给 Agent」，把复制的文字发回来（6.7）。两种答法你都按 [工具连接.md](工具连接.md) 4.6 处理，回复写在问题卡上，用户在工具里能看到。

**再次交付时**（处理过用户的答复）：在「拿到了什么」前面加一块「**这次处理了你的答复**」，逐条一行：问题、你的处理（就是 `reply.text`），改了结构的写上 id；还在等用户的（追问的、没答的）单独列出来。例：

> **这次处理了你的答复**
> - 厨房的门：朝餐厅那面的推拉门改成门洞，不装门；朝客厅那面还是墙（改了 o-kit-slide）。
> - 层高和窗台：都按 2800 / 900 / 450 / 2100，模型不用改。
> - 还在等你：哪几面墙承重（你说不知道，我先按图上最可能的保留，拆改前会再问）。

例：

> **你的户型 3D 白模（按图读出，待你确认）**
>
> **拿到了什么**（都在「交付」文件夹）
> - 方案.json：按图读出的结构底稿，要改就改它，我再重新出图。
> - 叠图.png：把读出的墙和门窗画回你的户型图，对不上的地方请告诉我。
> - 白模.glb：能转着看的三维白模。
> - 白模图/：西南、东北斜视和俯视；房间平视/：客厅两张、书房一张。
> - 附录.md：比例怎么定的、面积对照、哪些是推断。
>
> **怎么打开**：PNG 用看图软件；.glb 用支持 glTF 的查看器或建模软件（比如 Blender 自带导入）。在线查看器会把文件传给对方网站，用不用你定。方案.json 可以用「改改你的家」打开，见文末。
>
> **要你确认的**
> 1. 图上没标承重。书房和客厅之间、两间卧室之间这两道黑色粗墙是承重墙吗？现在都按隔墙画，拆改前我会先问你。
> 2. 餐厅北侧那段浅灰带是矮墙、栏板还是玻璃？多高？现在按约 1 米的矮墙画。
> 3. 客厅中间有一条横穿的虚线，是梁还是吊顶分界？现在没画进模型。
> 4. 书房标注 9.8 m²，按墙内量是 10.7 m²，差的 0.9 m² 接近窗边的飘窗台。窗台多深、多高、凸不凸出外墙？现在模型里它只是一扇窗。
> 5. 层高、窗台高、门高图上没有，我按 2800 / 900 / 2100 mm 假定，和你家一样吗？
>
> 比例来自上方和左侧两条尺寸链，两者一致（8 mm/像素）；其余房间面积和标注差不到 1%。
> 这是按图读出的结构，不是施工图；承重和拆改能不能做，要以现场和专业人员的结论为准。
>
> **下一步你可以**
> - 回答上面的问题，或者直接说哪里读错了：我改方案、重出图。也可以在「改改你的家」的「待核对」里答，答完点「把答复交给 Agent」，把复制的文字发给我。
> - 想看某个角度：说「我想看书房窗户那边」。
> - 试改造：说「把书房和客厅之间的墙拆掉看看」。这面墙承重不明，我会先问你一次。
> - 想自己动手拖墙、试装修、出改造清单 PDF：下载「改改你的家」（try-your-home.html，双击就能用，不联网，用法见 https://github.com/ai-azhou/try-your-home/blob/main/docs/USAGE.md ），打开「交付/方案.json」。改完在「导出」里存一份方案文件 JSON，回来说「我改好了」，告诉我文件在哪。

## 6.4 口径和禁语

| 不说 | 改说 |
| --- | --- |
| 结构准确、已核实、和现场一致 | 按图读出、待你确认 |
| 这面不是承重墙 / 这面可以拆 | 图上没有承重信息，我按隔墙画；能不能拆要现场和专业人员判断 |
| 拆了没问题、很安全、符合规范 | 方案里可以试这个改动看效果；可行性待专业确认 |
| 尺寸是 3.37 米（比图的精度还细） | 约 3.4 米（按图上尺寸链推算） |
| 推荐你用某某软件 / 某某网站 | 支持 glTF 的查看器都能打开，例如…… |

- 不替用户判断能不能拆、该不该改、怎么施工；只把图上看到的、推断的、不知道的分清楚说。
- 承重、外墙、管井、拆改相关的结论，一律写「可行性待专业确认」。
- 平视机位说明里写着「房间窄」的，照实告诉用户这间平视看不全，附俯视或斜视。

## 6.5 附录放什么

附录是给想细看的人的，可以长一些：

1. **比例证据**：每个来源的原文、原图像素端点、实际长度、轴线还是净尺寸、算出的 mm/px，来源之间的偏差。图片翻转、校正过的，写清步骤、校正用的四个点和校正前后的偏差。
2. **面积对照表**：逐间方案面积、标注面积、偏差，用的口径；单间偏差的推测和依据（[读图.md](读图.md) 2.7）。
3. **推断清单**：certainty 为 inferred / unknown 的构件，各一句依据。
4. **假设和缺省值**：层高、窗台高、窗顶高、门高、梁底高、矮墙高等，图上没有、用了缺省的，逐项列出。
5. **没做的检查**：例如没装 Pillow 没出叠图、翻拍图没做透视校正、弧墙按矢高近似。
6. **改造记录**（有改造时）：每条一句白话，标明已确认 / 待确认、是否在改造后的图里。
7. **怎么重出**：用到的命令（写成相对 `交付/` 的路径），方便以后照着重跑。

## 6.6 路线图：第 0 步怎么跟用户说

第一次回复（先回一句、查环境的那一条）里给路线图：你会做哪几步、每步交付什么、用户随时可以选什么。白话，五六行以内。原话样例（按图和用户的话改）：

> 这是一张开发商户型图，单层，上方和左侧有尺寸链。我打算这样做：
> 1. 按尺寸链定比例，读出墙、门窗、梁、房间，写成一份结构方案；
> 2. 把读出的结构画回你的图上自己核对，再问你 3–5 个图上读不出来的问题（承重、层高这类）；
> 3. 出能转着看的 3D 白模和几张白模图（斜视、俯视、你想看的房间）。
>
> 之后你随时可以说：只要结构就到第 2 步为止；想试拆墙、改门窗；想看装好大概什么感觉；想要一份改造清单 PDF。没特别说，我就按 1–3 做，做完告诉你下一步能做什么。

用户可选的目标，和你要做的：

| 用户想要 | 做哪些步（SKILL 的顺序） | 交付什么 |
| --- | --- | --- |
| 只要结构 | 1–5，再到 8 | 方案.json、叠图、问题；不出 GLB 和白模图，「下一步」里提一句可以出 |
| 要 3D 图 | 1–6，8 | 再加白模.glb、白模图、房间平视 |
| 试拆墙、改门窗 | 1–8 | 再加改造后的模型和图。承重、外墙、承重不明的墙先问一次（[改造.md](改造.md) 3.4）；最好先把承重那一问答了再试 |
| 看装好的感觉 | 1–6，8，再做 9 | 效果示意图（[生图.md](生图.md)）；先说清图会发给生图服务、只是示意 |
| 出改造清单 PDF | 1–8 写好 changes，再交给工具 | PDF 由「改改你的家」排版（全局「导出」→「改造清单 PDF」），你不生成 PDF；告诉用户怎么打开方案、在哪导出（6.7）。附录 6.5 的改造记录照写 |

用户中途换目标就按新目标往下走，已经做完、仍然有效的不重做。

## 6.7 下一步你可以：每次交付末尾

每次交付（包括改完再交、只备好生图素材）的说明最后加一段「**下一步你可以**」，3–6 条，只列眼下做得到的，每条一句话加一句用户可以照说的话。从下面挑：

- 回答问题 / 指出读错的地方（还有没答的问题时）：在对话里答，或者在「改改你的家」的「待核对」里答完点「把答复交给 Agent」，把复制的文字发给你。
- 看别的房间、别的角度（出过白模图以后）。
- 试改造（还没改过时）；看前后对比、确认等待中的改造（有 pending 时）。
- 让我帮你摆（出过白模以后；见 [装修.md](装修.md)）：可以照说「客厅北墙摆张三人沙发」「这面墙挂台 65 寸电视」，或者发一张家具的图，我照着画一个放进去。
- 看装好的感觉（出过白模以后；见 [生图.md](生图.md)）。
- **自己动手**：用「改改你的家」。每次都列这一条，写法见下。
- 出改造清单 PDF（有改造记录以后）：在工具里打开方案，全局「导出」→「改造清单 PDF」。

### 和「改改你的家」（try-your-home）怎么串

工具是一个离线网页文件，作者同一个人，仓库 https://github.com/ai-azhou/try-your-home （Gitee 镜像 https://gitee.com/gevoll/try-your-home ），给人看的用法在仓库的 `docs/USAGE.md`。双击打开就能用，不联网，不用装 Node。

**用户想自己动手**（拖墙、试装修、出改造清单 PDF）：

1. 告诉用户：在 GitHub（或 Gitee）上打开 `try-your-home.html` 的文件页，点「Download raw file」下载，双击用浏览器打开。
2. 在工具首页点「方案文件」或把 `交付/方案.json` 拖进去。方案里嵌了底图的（6.1 第 7 条），底图会直接显示。用 Chrome 或 Edge 打开的，工具会连着这个文件：你改完页面自动更新，他按 ⌘S 就写回原文件（[工具连接.md](工具连接.md) 4.2）。
3. 没连着（Safari、Firefox）：改完在顶栏「导出」→「方案文件 JSON」存一份。下载的文件名是方案标题加 `.json`（不一定叫 `方案.json`），一般在浏览器的下载文件夹。
4. 用户回来说「我改好了」：
   - 他是按 ⌘S 写回的：文件就是最新的，不用复制，从 `validate` 那步往下做。
   - 他是导出的：问清文件在哪，不要在下载文件夹里随便找一个同名文件就用。
   - 先备份 `$WORK/交付/方案.json`（比如复制成 `方案-之前.json`），再把导出的文件复制成 `$WORK/交付/方案.json`。文件里可能嵌着底图，别把整个文件读进上下文，要看字段用 `python3 -c` 或 jq 取。
   - `validate`；有 changes 再 `apply`。
   - `plan-cli questions <方案> --status answered`：用户在「待核对」里答了还没交给你的，在这里。有的话先按 [工具连接.md](工具连接.md) 4.6 逐条处理、写回复。
   - 和备份比一比改了哪里：原始结构变了（含按答复改的），两组模型和图都重出；只有 changes 变了，只重出改造后那组；只有问题卡的答复和回复变了，只重出叠图（6.1 第 4 条）。
   - 照常交付，「这次改了什么」逐条写 id；处理过答复的加「这次处理了你的答复」（6.3）。

**用户在「待核对」里答完、点了「把答复交给 Agent」，把文字贴回来**：按 [工具连接.md](工具连接.md) 4.6 处理。不用让他先导出方案文件——文字里有全部答复原文；他还有别的改动没导出时，文字里会说。

**用户本机有 try-your-home 仓库**（或者愿意 clone）：可以开本地服务模式，你改文件、他在页面上看，两边实时同步。命令以工具仓库 README 为准，现在是：

```sh
cd "<try-your-home 仓库目录>"
npm ci            # 第一次；要联网装依赖，先征得用户同意
npm run build     # 第一次或仓库更新后；生成 dist/index.html，服务要用它
node scripts/serve.mjs "$WORK/交付" 5180
```

- 需要 Node（工具仓库实测 Node 24）。第一个参数是**方案所在目录**，不是文件；端口可省，缺省 5180。服务只监听 127.0.0.1。
- 终端会列出可打开的地址（目录里每个 .json 一行，如 `http://127.0.0.1:5180/?plan=方案.json`），把那一行给用户。
- 服务会一直运行。放后台跑并记下它的 PID，用户说不用了再结束这一个 PID；或者让用户在那个终端按 Ctrl+C。不要按名字批量结束进程。
- 服务模式下改文件的规矩（改前重读、只改要改的、原子写、写完校验）见 [工具连接.md](工具连接.md) 4.2–4.3。

**用户在工具里点「交给 Agent」，把交接文字贴回来**：按 [工具连接.md](工具连接.md) 处理。交接文字里「方案文件」不是完整路径时，先问用户文件在哪。

写给用户的那一条，样例：

> - 想自己动手拖墙、试装修、出改造清单 PDF：下载「改改你的家」（try-your-home.html，双击就能用，不联网；用法 https://github.com/ai-azhou/try-your-home/blob/main/docs/USAGE.md ），打开「交付/方案.json」。改完在「导出」里存一份方案文件 JSON，回来说「我改好了」并告诉我文件在哪，我重新校验、重新出图。在工具里选中墙或门窗点「交给 Agent」，把复制的文字贴给我也行。
