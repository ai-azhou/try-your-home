# 1 格式：方案 JSON 怎么写

**什么时候读**：动手写或改方案 JSON 之前；校验报字段错误时；拿不准某个字段的单位、缺省值、能不能省略时。

本篇的事实以 core 和 schema 为准：`src/core/types.ts`（字段契约）、`src/core/io.ts`（文件单位换算）、`src/core/validate.ts`（几何校验）、`schema/plan.schema.json`（Skill 里是 `references/plan.schema.json`）。两者不一致时以代码为准，并报告给维护者。

## 1.1 单位：文件里所有长度都是 mm

| 量 | 单位 | 例 |
| --- | --- | --- |
| 平面坐标、墙厚、洞口宽和 offset、梁宽 | mm | `"thickness":240` |
| 高度：层高、墙高、矮墙高、洞底、洞顶、梁底、地面高差、楼层标高 | mm | `"ceiling":2800`，不是 `2.8` |
| 面积（只出现在命令输出和问题文字里） | m² | `stats` 的 `netArea: 65.8` |
| 角度：`north`、柱 `rotation` | 度 | `"north":0` |
| `evidence.pixelBox`、`underlay.origin`、`calibrations.p1/p2` | 原图像素 | `[88,88,712,112]` |
| `underlay.mmPerPx` | 每像素多少 mm | `10` |
| `underlay.opacity` | 0–100 | `50` |
| `panes[].width` | 相对比例，不是 mm | `[{"width":1,...},{"width":1,...}]` 两扇等宽 |

图上标的是米（如「2.80」「梁底 2.60」）就先换成 mm 再写：2.8 m → `2800`。问题文字里写长度也用 mm。

旧格式（version 2，高度用米）和更早的 legacy 格式可以读，但 Agent 新写的文件一律写 `"version":3`。**写成 `"version":2` 不会报错**：所有高度会被当成米读（2800 变成 2800 米高的墙），`validate` 照样 valid。写完核对一遍 version。

## 1.2 坐标与方向

- 平面坐标 x 向右、y 向下，和图片像素同向。原点自己定，常用外墙中心线的左上交点，或尺寸链的起点。所有楼层共用一个平面坐标系。
- 墙的方向 d = b − a，法向 **n = (−dy, dx) / |d|**。从左往右画的墙（d 指向右），n 指向屏幕下方；从上往下画的墙（d 指向下），n 指向屏幕左方。
- 用到 n 的字段：墙的 `bulge`（正值朝 n 鼓）、门的 `swing.side`（1 朝 n 开）。
- `north`：图的上方是 0，顺时针为正（北在图右方写 90）。只用于说明，命名机位 `iso-sw` 等按图纸轴，不按 north 旋转。

例：墙 a=[3000,0]、b=[3000,2000]，d=(0,2000)，n=(−2000,0)/2000=(−1,0)，指向西（屏幕左）。门开向东侧时 `side` 写 −1。

## 1.3 id

- 所有 id 在整个方案里唯一：墙、洞口、梁、房间、柱、管道井、楼梯、挑空、楼层、问题、改造记录共用一个命名空间。
- id 写了就不要改，问题卡的 `targets`、改造记录的 `target` 都靠它。建议用可读前缀：`w-n`（墙）、`o-bay`（洞口）、`b-1`（梁）、`r-master`（房间）、`col-1`、`sh-1`、`st-1`、`v-1`、`q-bearing`、`ch-1`。
- 局部拆墙会生成新 id：第二段是 `墙id~改造id`（如 `w-a~ch-3`），见 [改造.md](改造.md)。

## 1.4 顶层字段

工具还能导入一种给网页 Chat 用的简版格式（只有房间和门）。Agent 一律输出完整 v3，不要输出简版。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `format` | 是 | 固定 `"floorplan-structure"`；这是数据格式标识，和 Skill 名无关 |
| `version` | 是 | 固定 `3` |
| `title` | 是 | 方案名，字符串 |
| `ceiling` | 是 | 默认层高 mm，>0。图上没有就写 `2800` 并进问题卡或附录 |
| `walls` `openings` `beams` `rooms` `questions` `changes` | 是 | 数组，可以是空数组 `[]` |
| `north` | 否 | 度 |
| `levels` | 否 | 楼层，单层户型不写，见 1.7 |
| `columns` `shafts` `stairs` `voids` | 否 | 柱、管道井、楼梯、挑空；没有就省略或写 `[]` |
| `underlay` | 否 | 原图的比例和原点，见 1.6。要用 `overlay.py` 叠图就必须写 |
| `levelUnderlays` | 否 | 每层一份底图，键是楼层 id |
| `legacy` | 否 | 旧数据原样快照。**不要改、不要删** |
| `meta` | 否 | `planFile`、`source`、`createdAt`、`updatedAt`，都是字符串；工具保存时会写 |
| `decor` | 否 | 装修层。结构阶段不写；文件里已有就原样保留 |

顶层不许有别的字段（schema `additionalProperties:false`），拼错的字段名会被 `validate` 报 `schema` 错误。

## 1.5 构件字段

「缺省」一列说的是字段省略时 core 怎么算。表外的字段一律不许写。

### 墙 `walls[]`

| 字段 | 必填 | 单位 | 含义与约束 | 缺省 |
| --- | --- | --- | --- | --- |
| `id` | 是 | | | |
| `a` `b` | 是 | mm | 墙**中心线**两端点 `[x,y]`，不能重合 | |
| `thickness` | 是 | mm | >0 | |
| `kind` | 是 | | `exterior` 外墙 / `bearing` 承重墙 / `partition` 非承重隔墙 / `glass` 通高玻璃隔断 / `half` 矮墙（只有下部实体）/ `half-glass` 下部实墙加上部玻璃 | |
| `level` | 否 | | 楼层 id | 第一层 |
| `height` | 否 | mm | 墙顶离本层楼面的总高，>0 | 两侧相邻房间有效层高的最大值；两侧都没有房间时取本层 `ceiling`，再取顶层 `ceiling` |
| `lowHeight` | 否 | mm | 只对 `half`、`half-glass` 有用：矮墙实体高度，或玻璃下面实墙的高度；超过墙高时按墙高截断 | 1000 |
| `bulge` | 否 | mm | 弧墙：中心线圆弧相对 a–b 弦的**矢高**。正值朝 n 鼓，负值朝 −n 鼓 | 0（直墙） |
| `name` | 否 | | 给人看的名字，如「北外墙」 | |
| `evidence` | 见 1.6 | | | |

墙类型只是画法分类，不证明真实承重。`half` 在 `lowHeight` 以上什么都没有；`half-glass` 在 `lowHeight` 以上到墙高是玻璃；`glass` 整面是玻璃。

工具新建墙时的默认厚度（不是读图依据，只是没有任何信息时的起点）：exterior 240、bearing 200、partition 120、glass 80、half 120、half-glass 120。

### 洞口 `openings[]`（门、窗、门洞）

| 字段 | 必填 | 单位 | 含义与约束 | 缺省 |
| --- | --- | --- | --- | --- |
| `id` | 是 | | | |
| `wall` | 是 | | 宿主墙 id，直墙弧墙都行。洞口没有自己的 `level`，跟宿主墙 | |
| `offset` | 是 | mm | 沿宿主墙中心线，从 **a 端**量到洞口近端，≥0；弧墙按弧长量 | |
| `width` | 是 | mm | 沿墙宽度，>0；`offset + width` 不超过墙长；同一面墙上的洞口不能重叠 | |
| `kind` | 是 | | `door` 平开门 / `sliding` 推拉门 / `doorway` 门洞（无门扇）/ `window` 窗 / `floor-window` 落地窗 / `bay-window` 飘窗 / `open-balcony` 未封阳台（栏杆，无窗扇） | |
| `sill` | 是 | mm | 洞底离本层楼面，≥0 | 文件里必须写，解析器不会替你补 |
| `head` | 是 | mm | 洞顶离本层楼面，> sill，≤ 墙的有效高度。洞顶到墙顶之间自动生成过梁 | 同上 |
| `swing` | 否 | | 只对 `door` 有意义：`{"hinge":"start"\|"end","side":1\|-1}`。hinge 是铰链在洞口靠墙 a 端（start）还是 b 端（end）；side 是门扇开向 n 一侧（1）还是反侧（−1）。读法见 [读图.md](读图.md) 2.5 | `{"hinge":"start","side":1}`。缺省不等于「不知道」：开向读得出就写，读不出写缺省并把 evidence 写成 inferred |
| `panes` | 否 | | 分扇：`[{"width":比例,"kind":"fixed"\|"casement"\|"sliding"}]`，按比例铺满洞口。对窗、推拉门有效；直墙上的平开门写了 panes 在模型里仍是一整扇门（双开门在 name 或 evidence 里写明，并列进附录） | 推拉门两扇等宽；窗一扇固定 |
| `entry` | 否 | | 入户门写 `true` | |
| `name` `evidence` | 否 | | | |

图上没有洞口高度时，用下面的缺省值写 `sill` / `head`，并在 evidence 里写明是缺省（certainty 写 `inferred`），合并进问题卡或附录。这些数来自 core 的 `DEFAULTS`，是工具新建洞口的起点，不是图上读出的尺寸：

| kind | 新建宽度 | sill | head |
| --- | ---: | ---: | ---: |
| door / doorway | 900 | 0 | 2100 |
| sliding | 1600 | 0 | 2200 |
| window | 1500 | 900 | 2400 |
| floor-window | 2400 | 50 | 2500 |
| bay-window | 1800 | 450 | 2400 |
| open-balcony | 2400 | 0 | 2500 |

`bay-window` 在模型里只是墙上的窗洞和窗扇，**不会自动长出窗台或向外凸出**。要窗台，另写一个房间（见下方房间表的飘窗台写法）；向外凸出的飘窗要把凸出部分的墙画出来，见 [读图.md](读图.md) 2.4。`open-balcony` 生成 1100 mm 高的栏杆，从 sill 起算。

### 梁 `beams[]`

| 字段 | 必填 | 单位 | 含义 | 缺省 |
| --- | --- | --- | --- | --- |
| `id` | 是 | | | |
| `a` `b` | 是 | mm | 梁中心线端点 | |
| `width` | 是 | mm | >0 | 工具新建 240 |
| `bottom` | 是 | mm | 梁底离本层楼面，≥0。梁的实体从梁底一直到所在房间的顶 | 工具新建 2500 |
| `level` `name` `evidence` | 否 | | | |

### 房间 `rooms[]`

| 字段 | 必填 | 单位 | 含义与约束 | 缺省 |
| --- | --- | --- | --- | --- |
| `id` | 是 | | | |
| `name` | 是 | | 图上的房间名（无标注时按读图 2.4 推断并记 inferred） | |
| `poly` | 是 | mm | **墙内净边界**，顶点依次排列，至少 3 个，末点不重复首点，不自交，不能带内孔 | |
| `level` | 否 | | | 第一层 |
| `ceiling` | 否 | mm | 本房间层高，>0 | 本层 `ceiling`，再取顶层 `ceiling` |
| `floorOffset` | 否 | mm | 地面相对本层楼面的高差：高出为正（飘窗台 450），降板为负（卫生间 −50） | 0 |
| `use` | 否 | | 用途的自由文字 | |
| `counted` | 否 | | 是否计入使用面积；飘窗台、空调平台一般写 `false` | true |
| `evidence` | 见 1.6 | | | |

房间多边形不会自动扣除柱、管道井、挑空；面积统计就是多边形面积相加。飘窗台写法：主房间的 poly 把窗台那块让出来，另写一个房间 `{"name":"飘窗台","floorOffset":450,"counted":false,"poly":[窗台范围]}`，深度和高度图上没有就进问题卡。

### 柱 `columns[]`

| 字段 | 必填 | 单位 | 含义 |
| --- | --- | --- | --- |
| `id` `center` `shape` `size` `kind` | 是 | mm | `center` 中心点；`shape` 是 `rect` / `round`；`size` 是 `[宽,深]`，圆柱两个数都写直径且必须相等；`kind` 是 `bearing` / `decorative`，拿不准写 `bearing`（拆改要确认）并把 certainty 写 `unknown` |
| `rotation` | 否 | 度 | 绕中心旋转，缺省 0 |
| `level` `name` `evidence` | 否 | | |

柱的高度从本层楼面到本层层高，不能单独设。

### 管道井 `shafts[]`（烟道、管井、风道）

必填 `id`、`poly`（至少 3 点，不自交）、`kind`（`flue` 烟道 / `pipe` 管井 / `vent` 风道 / `other`，拿不准写 `other`）；可选 `level`、`name`、`evidence`。改造里一律不能删除，见 [改造.md](改造.md)。

### 楼梯 `stairs[]`

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | 是 | |
| `level` `to` | 是 | 起点楼层和终点楼层，必须不同，`to` 的标高更高。单层户型写不了楼梯 |
| `poly` | 是 | 平面占地 mm，至少 3 点 |
| `path` | 是 | 上行方向的踏步中心线，至少 2 个不重合的点，**从低处走向高处** |
| `width` | 是 | 梯段宽 mm |
| `kind` | 是 | `straight` / `L` / `U` / `spiral` |
| `steps` | 否 | 踏步数，正整数；缺省按每步不超过约 170 mm 高自动算 |
| `name` `evidence` | 否 | |

楼梯高度由两层 `elevation` 之差决定，不要写 `height` 字段。

### 挑空 `voids[]`

必填 `id`、`level`、`poly`；可选 `name`。表示这一层在 poly 范围里没有楼面（挑空、上层楼梯洞口都写）。**挑空没有 evidence 字段**，写了 schema 会报错；拿不准是不是挑空就进问题卡。

### 问题 `questions[]`

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `id` | 是 | |
| `text` | 是 | 问用户的原话 |
| `category` | 是 | `original` 原始信息 / `renovation` 改造意图 |
| `certainty` | 否 | `inferred` / `unknown`（为什么问） |
| `bbox` | 否 | 平面 mm 框 `[左,上,右,下]`，只框有歧义的构件；整屋问题不写 |
| `targets` | 否 | 涉及的构件 id 数组 |
| `options` | 否 | 选项字符串数组，用户仍可自由回答 |
| `level` | 否 | 复式里问的是哪一层 |
| `answer` `answeredBy` `answeredAt` | 否 | 答复；空或缺省 = 待答 |

问题卡没有 evidence 字段。怎么问见 [读图.md](读图.md) 2.8。

### 改造记录 `changes[]`

`{id, op, type, target?, data?, range?, note?, group?, by, status, confirm?, at?}`，写法和规则全在 [改造.md](改造.md)。改造记录没有 evidence 字段。

## 1.6 evidence：每个结构构件的依据

**写作规则（Agent 新写方案必须照做）**：

- 七类结构构件都带 `evidence`，并写 `certainty`：墙、洞口、梁、柱、管道井、楼梯、房间。
- `certainty:"seen"`（看到）：写 `basis`（依据）和 `pixelBox`（原图像素框）。
- `certainty:"inferred"`（推断）：写 `basis`；有像素框就附上。
- `certainty:"unknown"`（不知道）：`basis` 可以不写。
- 挑空、楼层、问题卡、改造记录不带 evidence。挑空拿不准就进问题卡。
- **不许为了凑格式编造像素框。** 构件在图上看不到（比如按惯例补的墙、只凭文字推断的窗台），就不写 pixelBox，certainty 也不能写 seen。
- **certainty 管整个构件**：门窗的位置和类型看到了，但洞口高度用的是缺省值，写 `inferred`（basis 写「高度缺省」）。
- **墙的 certainty 说的是「这面墙是什么类型」的把握**：图上标了承重、外墙或画法明确 → `seen`；按画法推断是隔墙 → `inferred`；看得见墙、看不出承不承重 → `unknown`，拆改要二次确认（[改造.md](改造.md) 3.4）。位置读不准写进 basis，会改结构的进问题卡。判法见 [读图.md](读图.md) 2.3。
- **「不编像素框」和「估读比例」不冲突**：底图的标定点、比例、原点是整张图的换算，允许估读，在 `calibrations` 的 note 写「估读」；构件的 pixelBox 是「这个构件画在图上哪里」的证据，定不准就不写。

schema 对 evidence 是宽松的（七类构件的 evidence 可省，basis、pixelBox 可省），那是为了兼容旧文件和工具里手画的构件；上面的规则比 schema 严，按规则写。

| 字段 | 含义 |
| --- | --- |
| `certainty` | 有 evidence 就必填：`seen` / `inferred` / `unknown` |
| `basis` | 一句话依据：「黑色实心粗墙带，约 24 px = 240 mm」「图上标注梁底 2.60」「三线窗符号；窗台高按缺省 900」 |
| `pixelBox` | `[x0,y0,x1,y1]`，**原图**像素（不是叠图放大后的像素），x0<x1、y0<y1，框住这个构件在图上的画法 |
| `confirmed` | 用户确认过：`{"by":"业主","at":"2026-10-29","note":"现场量过 45 cm"}`，`by` 必填非空 |

Skill 自带的示例 `assets/example/plan.json` 已按本节补齐：标「看到」的构件都有 pixelBox，框由底图的变换（`mmPerPx`、`origin`）从构件外包框换算得到，和原图一一对应。写法仍以本节和 1.8 的样例为准。

pixelBox 可以直接在图上量，也可以从你读出的 mm 坐标反算：px = mm / mmPerPx + origin。只有构件确实画在图上那个位置时才能反算；推断出来的构件不反算。

## 1.7 底图与楼层

- `underlay`：`{src, mmPerPx, origin, opacity, visible}` 必填，`mmPerPxY`、`rotation`、`flipX`、`flipY`、`calibrations` 可选。
  - `origin` 是平面坐标 (0,0) 在原图上的像素位置。换算：X = (x − ox) × mmPerPx，Y = (y − oy) × mmPerPxY（`mmPerPxY` 缺省等于 `mmPerPx`）。
  - `src` 是相对**方案文件所在目录**的路径：方案放 `$WORK/交付/方案.json`，原图放 `$WORK/原图.png`，`src` 写 `../原图.png`，交付前用 `embed_underlay.py "$WORK/交付/方案.json" "$WORK/原图.png"` 把原图嵌进方案，原先的 `src` 路径写法之后不再影响显示。
  - `calibrations`：`[{"p1":[x,y],"p2":[x,y],"length":mm,"note":"来源"}]`，记录定比例用的原图两点和长度。每个比例来源记一条；无依据时按读图 2.2 假设，note 必须明写「假设，非实测」。
  - 有镜像或旋转（`flipX`/`flipY`/`rotation`）时叠图位置会对不上，读图阶段不要写。
- 单层户型不写 `levels`，构件不写 `level`。
- 复式、跃层：`"levels":[{"id":"L1","name":"1F","elevation":0},{"id":"L2","name":"2F","elevation":3000,"ceiling":2700}]`。`elevation` 是楼面标高 mm，第一层 0，数组按标高严格递增；`ceiling` 缺省取顶层 `ceiling`。墙、梁、房间、柱、管道井、问题写 `level`（缺省第一层）；楼梯和挑空必须写。各层上下对齐：同一面外墙、同一部楼梯在各层坐标相同。
- 一张图并排画几层：每层一份 `levelUnderlays[层id]`，`src` 是同一张图，`origin` 取本层自己的像素原点，比例各层分别核；对位依据（楼梯、外墙角）写进 calibrations 的 note。

## 1.9 读写边界

- 每条命令读文件时先按 schema 检查字段形状（拼错字段名、缺必填、类型不对），再检查几何（宿主、重叠、自交、楼层引用）。错误码见 [命令.md](命令.md) 5.4。
- CLI 不会改写你的方案文件。会改写方案文件的只有 `embed_underlay.py`（以及工具的「保存」）：它们经过同一个转换边界，把文件重写成 v3 规范格式（键按字母排序、2 空格缩进），问题文字里写成米的长度会被改写成 mm（「2.8m」→「2800 mm」）；合法方案的内容不丢。文件有错误时 `embed_underlay.py` 直接失败、不改文件。所以改完方案先让 `validate` 通过，再嵌入底图或交给工具打开。
- `legacy` 里的 `__structureReplayFrame` 是内部瞬时标记，读写时会被清除，不能拿它控制改造重放。`legacy` 其余内容原样保留。
- 改文件时不要从头重建整个 JSON：先读出来，只改要改的字段，其余字段（包括你不认识的、`meta`、`legacy`、`decor`）原样写回。
