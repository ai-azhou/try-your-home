# 装修层数据格式草案（E1）

> 10-29 E1 设计稿。先不进 `src/`；定下来以后由 PM 改 `types.ts`，codex 写 core 和 schema。
> 契约仍以 `src/core/types.ts` 为准，本文只提议**一个新字段** `Plan.decor`，结构部分一个字段都不改。

## 1. 原则

| 原则 | 怎么做 | 为什么 |
|---|---|---|
| 装修是结构上的一层，不是结构的一部分 | `Plan.decor?: DecorLayer`，结构函数（`buildSolids`、`wallOutlines`、`applyChanges`、`validatePlan`）都不读它 | 结构阶段的代码和测试一行不用动；装修层坏了，结构照样能用 |
| 挂在「改造后」的结构上 | 装修里引用的墙、房间、洞口 id，都是 `applyChanges(base, changes).plan` 里的 id（含部分拆除生成的 `墙id~改造id`、改造里新加的墙） | 业主装修的是「改完以后的家」 |
| 装修不走改造记录 | 装修层直接存当前状态，不进 `changes` 重放 | 装修没有「原来」，全是新加的；撤销靠工具的历史，不靠重放 |
| 结构变了不偷偷改装修 | 挂不上的装修在解析时报问题（`DecorIssue`），数据原样保留，等用户决定 | 和「改造清单可看可撤销」同一个态度：不替用户删东西 |
| 单位和 v2 一致 | 平面位置、沿墙距离、厚度、进深用 **mm**；高度用 **m**；角度用度 | 和 `Opening.offset / sill / head` 同一套，Agent 不用记两套 |
| Agent 能写 | 每个装修构件都有 `by` 和 `status`，Agent 写的先是 `pending`，界面用淡紫画 | 和改造记录同一套「谁改的、确认没有」 |
| 自包含、零网络 | 用到的材料复制进 `decor.materials`；贴图只能是本地相对路径，禁止远程地址 | 和底图同一条隐私规矩；方案文件换台机器打开不丢东西 |

## 2. 顶层

```ts
/** 装修层：Plan 上的可选块。没有这个字段 = 还没开始装修 */
export interface DecorLayer {
  version: 1
  /** 当前整体风格：内置风格 id（'cream' 奶油原木 …）或 presets 里的自定义风格 id */
  style: string
  /** 方案里用到的材料。内置材料被用到时复制一份进来（自包含）；用户自定义颜色也在这里 */
  materials: Material[]
  /** 自定义风格：用户另存的、Agent 配的 */
  presets?: StylePreset[]
  /** 面的覆盖（地面、墙面、顶面）。没写的面 = 跟风格 */
  surfaces: Surface[]
  furniture: Furniture[]
  cabinets: Cabinet[]
  /** 造型：背景墙板、护墙板、格栅、踢脚线、拱形门套 */
  panels: Panel[]
  /** 用户画的壁龛和挖洞。柜子、家电的「嵌进墙里」由它们自己的 embed 字段派生，不存在这里 */
  recesses: Recess[]
  /**
   * 每个构件最后一次挂得上时的位置（平面 mm 外接框 + 所在墙面线段）。
   * 工具维护，Agent 不用写；墙被拆以后靠它把「没地方挂」的幽灵画在原处、推荐就近的墙。
   */
  cache?: Record<string, { level?: string; box: Box; face?: [Vec2, Vec2] }>
}

/** 所有装修构件共有 */
interface DecorBase {
  id: string
  name?: string
  /** 楼层：挂在墙上的跟墙走，自由摆放的（家具、岛台）写自己的；缺省第一层 */
  level?: string
  by: 'user' | 'agent'
  status: 'pending' | 'confirmed'
  /** 一句白话：想做什么 */
  note?: string
  /**
   * 受保护墙（承重 / 外墙 / 承重柱）上的嵌入：用户看过事实说明，点了「知道了」。
   * 这不是「允许」，只是「看过了」；改造清单照样列进「需要专业确认」。
   */
  ack?: { by: string; at?: string }
}
```

## 3. 墙面寻址：哪面墙、哪一侧、沿墙区间、高度区间

```ts
/**
 * 墙面 = 一面墙的一侧。side 和 Opening.swing.side 同义：1 = 墙法向 n 那一侧，−1 = 反方向。
 * （n = (−dy, dx) / |b − a|，见 types.ts NORMAL_CONVENTION）
 */
export interface FaceRef { wall: string; side: 1 | -1 }

/** 墙面上的一块：s 沿中心线离墙 a 端（mm，弧墙按弧长），z 离本层楼面（m） */
export interface FaceSpan { face: FaceRef; s: [number, number]; z: [number, number] }
```

**例子**（示例两室，改造后）：客餐厅的电视墙是西外墙 `w-w` 朝房间那一面。`w-w` 从 (0,0) 画到 (0,7200)，d = (0,1)，n = (−1,0) 指向室外，所以朝房间是 `side: -1`。墙内皮从 y = 120 到 y = 7080。

```json
{ "face": { "wall": "w-w", "side": -1 }, "s": [3780, 6220], "z": [0, 2.55] }
```

### 3.1 立面上的左右

站在房间里面对这面墙看（立面就是这么画的）：

- **`side = 1` 时，a → b 是从左到右**，立面横坐标 `u = s`；
- **`side = −1` 时，a → b 是从右到左**，`u = L − s`（L = 墙长）。

推导：看的方向 f = −side·n，平面 y 向下，人的右手方向 = (−f.y, f.x) = side·d。所以 d 和右手同向当且仅当 side = 1。界面和 Agent 交接文字都只说「左 / 右」，换算交给 core 的 `faceAxis(plan, face)`。

### 3.2 看得见的范围、跨墙的墙面

- **`faceExtent(plan, face) → [s0, s1]`**：墙面真正露在房间里的一段（被相邻墙挡掉的墙角不算）。从 `wallOutlines` 的轮廓算，界面和校验共用。上例 `w-w` 的 `[120, 7080]`。
- **一面「墙面」可能由几段共线的墙组成**（T 形交接处把一面长墙分成两条记录，或拆墙后两段连成一片）。`faceRun(plan, face)` 返回首尾相接、共线、朝同一侧的墙面链。构件**仍然锚在一段墙上**，s 允许超出这段墙的长度，超出部分落到链上的下一段；链断了（中间那段被拆）就报 `host-cut`。
  - 不引入新的「墙面实体」：v2 里墙才有 id，墙面是派生出来的；为它另造 id，改造一拆一合就要维护两套 id。代价是 Agent 写跨墙的造型时要知道「锚在第一段」，交接文字里会写明。是否改成显式实体，列进待讨论。
- **弧墙**：s 按中心线弧长（和洞口一致）；立面按墙面实际弧长展开，`u_face = s × R_face / R_center`。第一期弧墙上只能刷材质，不能做造型、挖、靠柜子（报 `arc-unsupported`），见探针 P1。

### 3.3 挂在别的东西上的东西

挖在造型板或柜子上的洞，不用墙面坐标，用**宿主的局部立面坐标**：`u` 从宿主左边起（mm，站在房间里看的左右），`z` 仍然离地（m）。这样造型挪了，洞跟着走。

## 4. 嵌入深度和「不挖透」

```ts
export interface Recess extends DecorBase {
  /** niche 壁龛（挖在墙上，可以空着、加层板）/ hole 挖洞（挖在造型板或柜子上） */
  kind: 'niche' | 'hole'
  host: { face: FaceRef } | { panel: string } | { cabinet: string }
  /** 墙上用 s（沿墙 mm）；造型、柜子上用 u（宿主局部 mm）；z 一律离地 m */
  rect: { s?: [number, number]; u?: [number, number]; z: [number, number] }
  /** 从宿主表面往里多深（mm）。'through' 只给造型和柜子：挖穿，露出后面的墙面 */
  depth: number | 'through'
  /** 龛里背板的材料，缺省同所在面 */
  back?: string
  /** 龛里层板离地高度（m） */
  shelves?: number[]
  /** 收边材料（1b） */
  trim?: string
}
```

柜子和家电「嵌进墙里」写在它们自己身上（`Cabinet.embed`、`Furniture.embed`，单位 mm），core 派生出一个等价的墙上嵌入，规则完全相同。这样一个嵌墙柜只有一份数据，Agent 改柜深时不会和一条单独的 Recess 打架。

**规则**（`validateDecor`，几何上的硬约束报 error，受保护只报 warn）：

| 代号 | 条件 | 级别 | 文案（只陈述事实） |
|---|---|---|---|
| `through-wall` | 墙上嵌入深度 ≥ 墙厚 | error | 「挖到 240 就穿了，那是开洞，属于结构改造。要开洞请到改造里加一个洞口」 |
| `meet-other-side` | 同一面墙两侧的嵌入在平面和高度上重叠，深度之和 ≥ 墙厚 | error | 「这面墙另一侧也挖了 150，两边加起来超过墙厚」 |
| `over-opening` | 嵌入和墙上的门窗洞口区间重叠 | error | 「这里是窗洞」 |
| `wall-kind` | 玻璃墙上嵌入；矮墙、半玻墙嵌入高过实体部分 | error | 「玻璃隔断上挖不了」/「矮墙只有 1.0 m 高」 |
| `out-of-face` | s 超出 `faceExtent` 或 `faceRun`；z 超出 0 到墙高 | error | 「超出这面墙了」 |
| `into-shaft` | 嵌入的平面范围压到管道井 / 烟道 | error | 「这里是管道井 / 烟道的位置」 |
| `host-depth` | 挖在造型 / 柜子上，深度大于宿主厚度 | error | 「造型只有 150 厚」；要再往里就是挖墙，按墙的规则重新判断 |
| `protected` | 宿主墙是 `bearing` / `exterior`（按改造后的类型，也看原始类型，和结构重放的保护规则一致） | warn | 「这面在方案里是外墙（读图看到）。在外墙上挖槽、嵌入能不能做、能挖多深，要专业人员到现场确认」 |
| `arc-unsupported` | 弧墙上嵌入 / 造型 / 靠柜 | error（第一期） | 「弧墙上的造型下一期做」 |

- **不设「至少留多厚」的数**：留多少算安全是专业判断，工具只把「墙厚 240 · 挖进 120 · 剩 120」三个数摆清楚（检查器俯视局部图）。
- **`protected` 不拦**：照画、照存，`ack` 记一下用户看过；锁的标记一直在，导出时进「需要专业确认」页。和拆承重墙的二次确认分开，因为嵌入不挖透，是「要问清楚」而不是「要拆掉」。是否也做成二次确认，列进待讨论。
- 「把握程度」也写进文案：墙的类型是读图推断（`evidence.certainty = 'inferred'`）时，文案说「读图推断是承重墙，没确认」。

## 5. 柜体的参数化描述

```ts
export interface Cabinet extends DecorBase {
  /** 高柜 / 地柜 / 吊柜：平面画法按这个分（设计规范 §4.3） */
  family: 'tall' | 'base' | 'wall'
  /** 靠墙：贴哪面墙、近端在哪（s，mm）、离墙面多远；或独立摆放（岛台）：中心点、角度 */
  place: { face: FaceRef; s: number; gap?: number } | { at: Vec2; rot: number }
  /** 宽（沿墙 mm）、柜深（mm，从墙面量，含嵌进墙里的部分） */
  width: number
  depth: number
  /** 柜底、柜顶离地 m（地柜 [0, 0.82]、吊柜 [1.55, 2.25] 是常见值，只做新建时的默认） */
  z: [number, number]
  /** 踢脚（底座）高 m；悬空柜、吊柜为 0 */
  plinth?: number
  /** 嵌进墙里 mm。>0 时派生一个墙上嵌入（规则见 §4） */
  embed?: number
  /** 台面：地柜、洞里的书桌板都用它 */
  top?: { material: string; thickness: number; overhang?: number }
  /** 分列，从左到右（站在柜子前面看的左右，和立面一致） */
  columns: CabinetColumn[]
  /** 跨格的洞：在柜子立面上画一个框，压到的格子被裁掉 */
  cuts?: { u: [number, number]; z: [number, number]; depth: 'through' | number }[]
  materials: { carcass: string; front: string }
  handle?: 'none' | 'bar' | 'knob' | 'edge'
}

export interface CabinetColumn {
  /** mm；各列之和 = width；最后一列可以省略，取剩下的 */
  width?: number
  /** 从下往上；各格高度之和 = 柜高 − 踢脚；最上一格可以省略 h */
  cells: CabinetCell[]
}

export type ApplianceType = 'fridge' | 'washer' | 'dryer' | 'oven' | 'steamer' | 'dishwasher' | 'microwave' | 'tv' | 'other'

export interface CabinetCell {
  h?: number
  /** 单开门 / 对开门 / 抽屉 / 上翻门 / 开放格 / 挖洞 / 家电位 */
  type: 'door' | 'doors' | 'drawers' | 'flap' | 'open' | 'void' | 'appliance'
  hinge?: 'left' | 'right'
  /** 抽屉个数；开放格里的层板数 */
  count?: number
  /** 挖洞：挖穿柜体露出墙面，或留一块背板（mm，从门板面往里挖多深）；洞里可以加一块台面 */
  void?: { depth: 'through' | number; top?: { z: number; overhang?: number; material?: string } }
  /** 家电位：放什么、外形（宽深 mm、高 m；缺省按家具库的常见尺寸） */
  appliance?: { type: ApplianceType; size?: [number, number, number] }
  /** 这一格门板单独换色 */
  material?: string
}
```

**例子**：书房书桌柜（样张 04）。靠西外墙，3 列；中间一列下面挖洞放书桌，上面开放格。

```json
{
  "id": "cab-desk", "name": "书房书桌柜", "family": "tall", "by": "user", "status": "confirmed",
  "place": { "face": { "wall": "w-w", "side": -1 }, "s": 280 },
  "width": 3100, "depth": 400, "z": [0, 2.8], "plinth": 0.08,
  "columns": [
    { "width": 900,  "cells": [ { "type": "doors" } ] },
    { "width": 1400, "cells": [
      { "h": 1.47, "type": "void", "void": { "depth": "through", "top": { "z": 0.73, "overhang": 200 } } },
      { "h": 0.62, "type": "open", "count": 1 },
      { "type": "open", "count": 1 } ] },
    { "cells": [ { "h": 0.67, "type": "drawers", "count": 2 }, { "h": 0.80, "type": "open" }, { "type": "door", "hinge": "left" } ] }
  ],
  "materials": { "carcass": "oak-veneer", "front": "cream-matte" }, "handle": "bar"
}
```

- 列宽、格高都存「数」，不存「比例」：业主和专业人士沟通时说的是「中间那格 1.4 米」。
- `s: 280` 是柜子近端离 `w-w` 的 a 端 280mm；因为 `side = −1`，它在立面上是**右端**（北边）。界面不让人碰这个换算。
- 这套描述在 3D 里能直接生成：柜体 = 外框盒子减去 void 和 cuts（全是轴对齐盒子，不需要通用 CSG），门板 = 每格一块薄板，开放格 = 层板。探针 P3 验证。

## 6. 造型

```ts
export interface Panel extends DecorBase {
  /** 背景墙板 / 护墙板 / 格栅 / 踢脚线 / 拱形门套 */
  type: 'feature' | 'wainscot' | 'slats' | 'skirting' | 'arch'
  /** 贴在哪面墙的哪一块；arch 用 opening 定位，不写 span */
  span?: FaceSpan
  opening?: string
  /** 出墙厚度 mm（含龙骨、基层） */
  thickness: number
  material: string
  /** 分缝：竖缝 / 横缝，间距、缝宽 mm */
  grooves?: { dir: 'v' | 'h'; spacing: number; width?: number }
  /** 护墙板的框线 */
  frame?: { style: 'flat' | 'raised'; margin: number }
  /** 格栅：条宽、间隙、条深 mm */
  slats?: { width: number; gap: number; depth: number }
  /** 拱形门套：拱顶半径 mm，缺省 = 洞宽 / 2（半圆拱）。只在原门洞里做，不改洞口 */
  arch?: { radius?: number }
  /** 遇到门窗：缺省自动让开（造型板上扣掉洞口） */
  avoid?: 'openings' | 'none'
}
```

- **归类规矩（10-29 本人定）**：贴墙面、不分隔空间的放这里；自立、分隔空间的（比如弧形隔断）去改造里加墙。拱形门套是「贴在已有门洞上的石膏板」，不是改洞口，所以在这里；要把洞口真的改成拱形，是结构改造（`Opening` 以后加洞顶形状，列进待讨论）。
- 踢脚线通常跟风格（`StylePreset.trims.skirting`），只有某面墙要换色、取消时才写一条 `skirting` 覆盖。

## 8. 材料、风格和「面的覆盖」

```ts
export type MaterialCategory = 'wood-floor' | 'tile' | 'stone' | 'paint' | 'texture-paint' | 'wallpaper' | 'veneer' | 'microcement' | 'laminate' | 'fabric' | 'leather' | 'metal' | 'glass' | 'rattan' | 'other'

export interface Material {
  id: string
  name: string
  category: MaterialCategory
  /** 真实色 sRGB。卡片色块、立面用它；平面显示时界面统一压低彩度（设计规范 §2.3），数据里不存第二份 */
  color: string
  /** 2D 轻量纹理（按真实尺寸画） */
  texture?: { kind: 'planks' | 'tiles' | 'herringbone' | 'grain' | 'speckle' | 'veins' | 'weave'; size?: [number, number]; joint?: number }
  /** 3D 以后用：PBR 子集。现在只存不用；贴图只能是本地相对路径 */
  pbr?: { roughness?: number; metalness?: number; sheen?: number; maps?: { base?: string; normal?: string; rough?: string } }
  /** 用户自己写的备注（品牌、色号）。工具不联网查，也不推荐品牌 */
  ref?: string
}

/** 材料角色：风格预设按角色给材料，面和构件按角色取 */
export type MaterialRole =
  | 'floor.main' | 'floor.wet' | 'floor.outdoor' | 'threshold'
  | 'wall.main' | 'wall.wet' | 'wall.accent' | 'ceiling' | 'skirting'
  | 'wood.main' | 'cabinet.front' | 'cabinet.carcass' | 'stone.top' | 'metal'
  | 'fabric.main' | 'fabric.accent' | 'rug'

export interface StylePreset {
  id: string
  name: string
  blurb?: string
  roles: Partial<Record<MaterialRole, string>>
  /** 房间规则：名称或用途里含这些字的房间用哪个地面 / 墙面角色。缺省：卫、厨、阳台 → 湿区 */
  rooms?: { match: string[]; floor?: MaterialRole; wall?: MaterialRole }[]
  trims?: { skirting?: { height: number; role: MaterialRole }; threshold?: boolean }
  /** 风格卡上材料板用哪几块（4–6 块） */
  board?: string[]
  by?: 'builtin' | 'user' | 'agent'
}

export type SurfaceTarget =
  | { floor: string }
  | { ceiling: string }
  /** 墙面：不写 s / z = 整面；写 s = 一段；写 z = 到某个高度（双色墙、护墙漆） */
  | { face: FaceRef; s?: [number, number]; z?: [number, number] }

export interface Surface {
  id: string
  target: SurfaceTarget
  material: string
  /** 铺法：直铺 / 错缝 / 人字拼 / 鱼骨拼 / 对缝 / 斜铺；砖的规格、起铺点、角度 */
  layout?: { pattern: 'straight' | 'staggered' | 'herringbone' | 'chevron' | 'grid' | 'diagonal'; size?: [number, number]; origin?: Vec2; angle?: number; joint?: number }
  by: 'user' | 'agent'
  status: 'pending' | 'confirmed'
}
```

**一块面最后是什么材料**（`resolveFinish`），从上往下取第一个有的：

1. `surfaces` 里针对这块面的覆盖（「单独改过」）；
2. 构件自己写的材料（柜门、台面、造型板）；
3. 风格的房间规则（卫生间 → `floor.wet`）；
4. 风格的默认角色（`floor.main`、`wall.main`）；
5. 都没有：白模中性色（和结构态一样的白）。

换风格 = 只改 `decor.style`；「保留我单独改过的」= 不动 `surfaces`；不保留 = 清空 `surfaces` 里 `by: 'user'` 的覆盖（先进撤销历史）。

**2D 和 3D 复用**：2D 只用 `color` + `texture`（平涂 + 线条纹理）；3D 第一档用同一个 `color` 平涂（探针 P1–P3 的白盒），第二档读 `pbr`；`texture.size` 是真实尺寸，3D 里就是 UV 缩放。所以现在填的数据以后不用重填。

## 9. 结构改了以后：解析和重新挂接

```ts
/** 每次结构或装修变了都重算；不改数据，只给界面和导出用 */
export function resolveDecor(plan: Plan /* 改造后 */, decor: DecorLayer): {
  placed: { id: string; footprint: Vec2[]; face?: { a: Vec2; b: Vec2; side: 1 | -1 }; level: string }[]
  issues: DecorIssue[]
}
export interface DecorIssue {
  id: string            // 出问题的构件
  code: 'host-missing' | 'host-cut' | 'out-of-face' | 'too-deep' | 'wall-kind' | 'over-opening'
      | 'through-wall' | 'meet-other-side' | 'into-shaft' | 'host-depth' | 'protected' | 'room-missing' | 'arc-unsupported'
  level: 'error' | 'warn' | 'info'
  text: string          // 中文一句话（英文在 ui 层翻译）
  /** 界面给的选项：挪到别的墙 / 裁到剩下的墙上 / 先留着 / 删掉 */
  fix?: ('move' | 'clip' | 'keep' | 'delete')[]
}
```

| 结构上发生了什么 | 挂在上面的装修 | 代号 |
|---|---|---|
| 整面墙拆了 | 留着，按 `cache` 画成柠檬虚线幽灵；选项：挪到别的墙（推荐最近的同朝向墙面）/ 先留着 / 删掉 | `host-missing` |
| 拆了一段（`range`） | 完全落在剩下某一段上的：**重新挂到那一段**（第二段 id `墙id~改造id`，s 换算），不报问题——和洞口的规则一样；跨过拆掉那段的：选项「裁到剩下的墙上 / 挪 / 删」 | `host-cut` |
| 墙变短、墙角挪了（`moveJoint`） | 保持离 a 端的 s；超出看得见范围的报问题，选项「夹回墙内 / 挪 / 删」 | `out-of-face` |
| 墙变薄 | 嵌入深度 ≥ 新墙厚 | `too-deep` |
| 墙类型改成玻璃 / 矮墙 | 嵌入、靠柜挂不住 | `wall-kind` |
| 新开了洞口，压到嵌入或柜子 | 造型板自动让开洞口；嵌入、柜子报问题 | `over-opening` |
| 房间删了、合并了 | 地面覆盖失效，退回风格默认 | `room-missing`（info） |
| 靠墙的家具（`against`）那面墙动了 | 家具跟着贴过去；墙没了就原地不动，去掉 `against` | info |

- 这些都只在解析里报，**数据原样保留**；用户点了选项才改数据（进撤销历史）。
- 改造态里，选中挂着装修的墙时检查器多一行事实：「这面墙上有 2 项装修（电视背景墙、嵌墙柜）」。删墙的确认里也写这句。不拦。
- 撤销结构改造（改造清单里撤销一条），挂在被撤销的新墙上的装修同样变成 `host-missing`。

**镜像**（`mirrorPlan` 同步镜像装修）：家具 `at` 镜像、`rot` 镜像；`FaceRef.side` 取反（和洞口 `swing.side` 一样），`s` 不变；立面左右因此自动翻过来，柜子 `columns` 顺序反过来、`hinge` 左右互换，铺法角度镜像。镜像只在原始模式可用（现状），装修层里已有内容时，镜像前提示一句「装修会一起镜像」。

## 11. 还没定的

- 墙面要不要成为显式实体（`faces[]`，跨多段墙）——现在的方案是锚在一段墙上、允许沿共线链延伸。
- 家具高度单位用 m（和 v2 一致）还是 mm（柜子、家具业内习惯）——草案按 v2 用 m，界面里柜子内部尺寸显示 mm。
- 装修层要不要分楼层存（`levels` 下各一份）还是平铺 + `level` 字段——草案平铺，和结构构件一致。
- 一套方案能不能存两套装修（A/B 风格对比）——草案不支持，见待讨论。
